A launcher that can stay—and prove it belongs

How PortReeve adds foreground stack sessions and verified activation without turning its daemon into a shell server or treating a PID as durable truth.

BackgroundIntuitionCodeCasesQuiz

Background

Before this pull request, the launcher engine could run finite commands: Start invoked a project command, waited for it to finish, inspected fresh listeners, and completed a renewable daemon operation. That fits a command such as docker compose up -d. It does not fit a launcher that deliberately stays in the foreground for as long as the stack is running.

There was a second boundary too. Command-only launchers could show that the assigned ports had listeners, but a listener proves occupancy—not who started it. PortReeve already had a stronger activation protocol in which a project launcher begins an exact allocation generation, renews pending endpoint leases, and confirms providers with fresh process or Docker evidence. The launcher engine did not yet require that proof.

Prepared

Ports form one immutable generation.

Observed

Listeners exist, but ownership is not proven.

Verified

Activation, generation, provider, and listener agree.

Conflicting

Fresh ownership facts disagree.

The design constraint: the application that invokes a project command owns its child process group. The daemon owns allocation and renewable coordination. Neither authority is allowed to quietly absorb the other.

Intuition

An attached Start is like keeping a hand on a physical switch. The CLI or Desktop main process starts one isolated process group and remains tied to it. Output can continue to flow, Status and Stop can still run as short companion operations, and an explicit termination action can signal exactly the group that application created.

Verified activation adds a second test after shell execution. Exit code zero answers “did the shell report success?” Fresh PortReeve evidence answers “did the intended generation become a confirmed stack?” Verified mode requires both.

PORTREEVE_STACK_ID=stack-123
PORTREEVE_GENERATION_ID=generation-456
PORTREEVE_SOCKET=/Users/me/Library/Application Support/PortReeve/portreeve.sock

# The project launcher uses those facts to:
# 1. begin generation-456
# 2. renew its endpoint leases
# 3. start and confirm providers
# 4. clean up failures
# 5. end activation after Stop
What is deliberately not provided: persistent detach/reattach, adoption after caller loss, a generic daemon shell, interactive PTY input, or “whatever is listening must be ours.”

Code walkthrough

One command primitive, two lifetimes

command-session.js now builds a common POSIX session. Finite commands add a timeout. Attached commands do not. Both use a login shell, closed stdin, separate process group, bounded retained tail, and the same graceful-then-force termination policy.

An application-local registry

AttachedCommandRegistry keys one session by canonical stack root. It exposes inspection for close guards and termination by root, removes the handle when the child settles, and refuses a second local attached Start. No identity is persisted or sent to the daemon.

Termination remains instance-bound

The handle signals -processGroupId, not a port listener and not an arbitrary caller-supplied PID. Before the first signal it checks whether the child has already reported exit; that closes the small window in which an exited group number could be mistaken for a live session. SIGTERM is followed by SIGKILL only after the configured grace period and only for the group created by this command session.

Attached coordination composes with finite work

The lifecycle service begins attached Start with executionMode: attached. The daemon's existing per-root rules allow one finite Status or Stop beside it. Stop invokes only the trusted project Stop command; it never terminates the group. Attached Restart is not a custom long-running restart command: it completes finite Stop, revalidates, then begins attached Start.

Verification may happen before an attached command exits

A foreground launcher often becomes healthy and then remains alive. The engine therefore polls fresh daemon evidence while the command runs. If the supplied generation becomes verified, that matching snapshot is retained for the operation's maturity result. When the command eventually exits after a later Stop, terminal evidence may correctly say stopped while the safe operation record still says that this run achieved verification.

Strict, reduced history

The public operation completion schema gains one nullable integration summary: declared mode, whether exact matching proof appeared, whether a command-only launcher merits an upgrade suggestion, generation ID, and activation ID. It still rejects commands, environment values, process identities, credentials, and raw output. Existing stored completions remain readable because the new field defaults to null.

Maturity changes are deliberate

A command-only run that happens to perform the complete activation transaction does not rewrite the project file. It reports an upgrade suggestion. Moving the checked-in launcher from verified activation back to command-only requires an explicit transition confirmation; the resulting bytes must then earn normal exact-revision trust.
