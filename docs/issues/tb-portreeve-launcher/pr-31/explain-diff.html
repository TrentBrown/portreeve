Giving the Desktop a key, not a master key

How PortReeve makes launcher files, commands, output, and attached processes usable from Electron while keeping filesystem and process authority in the trusted main process.

BackgroundIntuitionCodeCasesQuiz

Background

By the end of PR #30, PortReeve already had a shared launcher engine. It could read a checked-in launcher, resolve allocated endpoints into environment variables, run finite or attached commands, coordinate same-root operations through the daemon, and evaluate fresh listener or activation evidence. The CLI could use all of this directly because it is itself a trusted local process.

An Electron renderer is different. It presents HTML and JavaScript, and therefore must be treated as an untrusted display surface even when all its current code is ours. Giving it a generic file path, shell command, process group ID, or filesystem method would turn a future renderer bug into local machine authority.

Main process keeps

Canonical roots, file handles, exact revisions, runtime objects, abort controllers, process-group ownership, raw session output, and save dialogs.

Renderer receives

Opaque document and session IDs, reduced evidence, bounded output views, safe history, named actions, and strict success or failure results.

The central rule: the renderer may ask PortReeve to perform one named operation, but it may not assemble its own filesystem or process operation from primitive capabilities.

Intuition

Think of a hotel cloakroom ticket. The ticket lets its holder retrieve or discuss one deposited coat; it does not reveal the storeroom layout or open every door. PR #31 gives the renderer document and session tickets. Electron main resolves them to the real root, revision, runtime session, or save destination.

Long-running attached Start makes this separation especially important. The first IPC call returns immediately with a random session ID. Main keeps an AbortController, the one-megabyte output tail, and the shared lifecycle promise. Later IPC calls can inspect output, cancel the session, or request exact attached termination without ever seeing a PID.

// Reduced response

  state: "running",
  output: { chunks: [], retainedBytes: 0, truncated: false }
}

// Not present: root path, shell path, command, environment, PID, process group

Code walkthrough

Launcher documents

The main adapter opens a known stack into an opaque document handle. Save uses exclusive creation for a missing file or exact-revision replacement for a known file. External changes return a conflict. Explicit overwrite may replace invalid bytes, but it re-reads a valid current document so downgrade confirmation cannot be bypassed.

Exact saved trust

Only after the atomic write succeeds does main trust the returned revision. The response contains the new reduced document state—not the canonical root or an arbitrary filename supplied by the renderer.

Opaque asynchronous runtime sessions

launcher-adapter.js starts shared lifecycle execution without holding an IPC request open. Output chunks are split to strict event bounds and appended to the same UTF-8-safe one-megabyte tail used by command sessions. The adapter retains no more than twenty terminal output sessions, while running sessions remain available until completion.

Close protection covers the dangerous interval

An attached launcher session is marked from the trusted checked-in definition. The BrowserWindow close guard blocks while that Start or Restart is running—from trust and daemon admission, through process creation, until the command becomes terminal. This matters because checking only the local process registry leaves a narrow pre-spawn interval in which the operation is active but its group has not appeared yet.

Strict IPC is a capability list

Shared Zod schemas define launcher snapshots, document mutations, actions, sessions, output, saving, termination, and blocked-close state. IPC accepts only the trusted main renderer frame. Preload exposes individual methods such as openLauncherDocument(stackId) and cancelLauncherSession(sessionId); there is no generic invoke, read-file, write-file, shell, or signal method.

History is durable; raw output is not

The renderer can see the latest twenty daemon operation records after main removes stack roots and caller identities. Raw stdout and stderr stay only in this application session. Save output opens a native main-process dialog and writes only to the user-selected path; the renderer supplies no destination.

The earlier lifecycle failure is now actionable

The existing Overview operation result gains the failed step, stable code and message, exit or timeout state, reduced before/after evidence, and a bounded output tail when one is available. Install followed by unhealthy supervision is specifically reported as a health-verification failure rather than the earlier generic “failed without completing” box.
