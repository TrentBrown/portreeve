Background

The daemon needed shared truth before launchers could be shared

The approved Launcher design allows both the Desktop app and CLI to operate a stack. If they decide independently, two starts can race, a stop can collide with a restart, and a dead controller can leave the system believing work is still active.

P2 does not execute commands. It establishes the coordination protocol and persistence on which the later shared execution engine will rely.

Before

There was no daemon-owned operation session, credential, renewable deadline, or safe launcher history.

After

Every launcher action can begin, renew, complete, inspect, and list through the official socket protocol.

The returned credential is a bearer secret for that one operation. The client holds it; SQLite stores only its SHA-256 hash. A healthy controller renews about every ten seconds. Each successful renewal moves the deadline thirty seconds forward.

Expiry means “the coordinator stopped reporting.” It deliberately does not mean “the daemon should adopt, signal, or kill a process.” The later execution layer owns process behavior.

Public client lifecycle

  operation: "start",
  executionMode: "attached"
});

await client.renewLauncherOperation(
  session.operation.id,
  session.credential
);

await client.completeLauncherOperation(
  session.operation.id,
  session.credential,
  { outcome: "succeeded" }
);

Admission rules

A BEGIN IMMEDIATE transaction serializes decisions even when two clients use different database connections. Independent stack roots remain concurrent. One attached Start may admit one finite Status or Stop companion, but conflicting work on the same root is refused.

While an operation is active, PortReeve also blocks changed stack definitions, deletion, and pruning. That prevents coordination rows from silently changing meaning underneath a running launcher.

Safety boundary

What the daemon stores—and what it refuses to become

Stored

  • operation and execution mode
  • timestamps and duration
  • generation identity
  • outcome and exit code
  • bounded evidence and failure summaries

Not stored

  • shell commands
  • environment values
  • plaintext credentials
  • raw stdout or stderr
  • process adoption or kill intent

Strict schemas reject extra fields, so command text or secrets cannot hitchhike in an otherwise valid payload. Inspection requires no credential, but mutation does. Completion is idempotent only when the normalized metadata is identical.

Each stack retains active rows plus its latest twenty terminal records. Begin, completion, and loss also enter PortReeve's existing bounded global history.

Verification

Proven against real persistence and the public socket

  • 114 focused tests, 483 assertions, zero failures.
  • Real SQLite cross-connection races and migration coverage.
  • Real Bun server, private Unix socket, and official client.
  • npm tarball consumed from Node, preserving the portable-client boundary.
