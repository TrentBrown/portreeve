The launcher reaches the command line

How checked-in project commands become an approachable, trusted CLI workflow—while allocation, evidence, and command execution keep their separate authorities.

BackgroundIntuitionCodeCasesQuiz

Background

A PortReeve stack describes components and endpoints, and the daemon assigns a coherent generation of host ports. A project still owns the operational knowledge: perhaps bun run start starts the API, docker compose down stops it, and make status reports application-specific detail.

Earlier launcher pull requests supplied a strict portreeve.launcher.json, exact-byte trust, endpoint environment resolution, listener evidence, renewable daemon coordination, and safe finite process execution. Until this change, those pieces were library capabilities. PR #29 turns them into seven ordinary Commander commands.

init

Suggest, preview, create, and trust.

validate

Check even an unapplied hand edit.

trust

Review exact executable meaning.

lifecycle

Start, Stop, Restart, or Status.

The key boundary: the CLI executes a trusted project command through the shared launcher engine. The daemon continues to allocate, observe, and coordinate; it never becomes a generic shell server.

Intuition

The workflow has two distinct moments of consent. First, a human reviews what a launcher means and trusts one exact file revision. Later, if live evidence makes a particular operation risky, the caller grants narrow operation-specific consent. Trust is not a blanket “force” switch, and force is not a substitute for trust.

Code walkthrough

One shared runtime

launcher/runtime.js constructs the official socket client, private local-state store, environment resolver, evidence service, and lifecycle service. Commander does not invent a parallel implementation; this factory is also the natural future Electron-main boundary.

Root and authority selection

launcher-selection.js discovers the nearest stack definition independently of Git or canonicalizes --stack-root. Normal execution selects the applied stack from the daemon. Only a proven daemon outage permits a cached applied-stack snapshot.

Interactive setup remains intentionally small

launcher init inspects only known manifests in the selected directory and never executes them. It shows unambiguous suggestions with provenance, leaves ambiguous operations for the user, supplies endpoint mapping suggestions, normalizes the exact JSON, and uses exclusive file creation. If a file already exists, the CLI points the user to normal editing, validation, and trust rather than becoming a terminal editor.

Trust reviews resolved behavior

A platform-neutral file may say "shell": "system". The trust review must say which executable that means here—such as /bin/zsh—along with the canonical working directory, operation timeout or mode, complete command strings, and exact SHA-256 revision. A newline-only external edit changes the revision and removes effective trust.

Human and automation output do not collide

Human mode streams command chunks and ends with evidence and failure summaries. JSON mode suppresses live chunks and emits one versioned document containing the already bounded result. Exit codes separate ordinary command/state differences (10), policy conflicts (20), unavailable authority (30), and invalid input (50).

Fresh-process degraded operation needs one more cached fact

The lifecycle engine validates a full applied stack record before it can inspect cached endpoints. A newly launched CLI process has no in-memory copy after the daemon goes away, so PR #29 stores the last nonsecret applied StackRecord beside the existing exact-revision environment cache. It never synthesizes durable authority from the project JSON.
