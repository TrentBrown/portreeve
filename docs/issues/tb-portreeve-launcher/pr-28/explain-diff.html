Finite launcher execution

How a trusted project command becomes a bounded, coordinated, evidence-aware local stack operation—without turning the PortReeve daemon into a shell runner.

Background

PortReeve already knows three different kinds of facts. A stack definition says which components and endpoints exist. An allocation generation assigns coherent host ports. Fresh listener and activation evidence says what is actually observable now. What PortReeve deliberately does not know is how a particular project starts its API, stops Docker Compose, or checks its own health.

The checked-in portreeve.launcher.json bridges that gap with trusted shell commands and endpoint-to-environment mappings. Earlier pull requests supplied strict configuration, exact-revision trust, daemon coordination sessions, environment resolution, and evidence classification. This PR connects those pieces to real finite commands.

The authority boundary: the Desktop or CLI process executes project commands. The daemon allocates ports, reports evidence, and serializes operations. It never receives a command, environment value, or raw terminal output.

Intuition

Think of one lifecycle request as a short transaction with an external side effect. PortReeve first takes a trustworthy snapshot, then asks the daemon for a renewable “operation ticket.” The shell command runs locally while the ticket prevents a second incompatible caller. Finally, PortReeve observes the world again and closes the ticket with safe metadata.

A concrete example

Allocated endpoint: api.default → 127.0.0.1:43100
Launcher mapping:   API_PORT     → host-port
Executed command:   npm run dev
Injected values:    API_PORT=43100
                    PORTREEVE_GENERATION_ID=...
Fresh result:       command exited 0; listener evidence is fully-observed
Durable history:    outcome + timing + evidence (no API_PORT, no terminal text)

Exit zero does not mean “PortReeve owns this listener.” In command-only mode it means only that the project command succeeded. Fresh evidence remains a separate statement.

Code walkthrough

Command session

command-session.js resolves the supported login shell and spawns it with -l -c, a contained working directory, closed stdin, piped stdout/stderr, and detached: true. On POSIX that child PID is also the new process-group identity.

Lifecycle service

lifecycle-service.js freezes a normalized trusted snapshot, evaluates evidence, resolves current values, manages the renewable daemon session, invokes command sessions, refreshes evidence, and returns structured details.

Termination is narrow

Timeout or cancellation sends SIGTERM to the negative recorded child PID—the exact process group created for this command. After a short grace period, SIGKILL may target that same group. PortReeve does not search by port, signal an inferred owner, or automatically run Stop.

process.kill(-processGroupId, 'SIGTERM')
// grace period
process.kill(-processGroupId, 'SIGKILL')

Output is useful but deliberately ephemeral

Chunks stream immediately with stdout/stderr identity. Retention keeps only the newest one megabyte, preserves UTF-8 character boundaries, and inserts a visible truncation marker. A composed Restart shares this operation-wide cap across Stop and Start. The daemon sees none of it.

Coordination does not race completion

The operation ticket renews every ten seconds. Losing renewal aborts the local command group. If a renewal is already in flight when a fast command finishes, completion waits for that renewal to settle, preventing renew and complete from racing at the daemon.

Lifecycle cases

Stopped

Start prepares or reuses a generation, then runs normally.

Partial

Start requires explicit Run Start Anyway and retains the current generation.

Fully observed

Start refuses and points toward Status or Restart.

Verified

Start refuses because a verified activation is already live.

Conflicting

Start and Restart refuse; reclamation remains a separate authorized workflow.

Uncertain

Mutation refuses until evidence is trustworthy again.
