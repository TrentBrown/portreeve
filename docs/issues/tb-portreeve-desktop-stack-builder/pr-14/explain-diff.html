One runnable stack, one authoritative root

Portreeve used to let Git decide where a stack lived. This change gives that decision back to the developer: a stack is anchored at the exact directory selected for the runnable system, even when that directory contains several repositories.

Background

A Portreeve claim is the durable identity of one service endpoint. Standalone claims still use workspaceRoot, normally derived from the Git worktree. A stack is broader: it describes several components, their endpoints, and dependency addresses as one independently runnable local system.

The old stack API reused the claim term workspaceRoot and canonicalized it through Git. That worked for one-repository projects, but consider a runnable customer stack containing two repositories:

/customer-stack/             ← the runnable system
  portreeve.stack.json
  api-repository/.git/
  web-repository/.git/

Running a command inside web-repository asked Git for its top-level directory, producing /customer-stack/web-repository. The real orchestration boundary was /customer-stack. Git answered a valid Git question, but the wrong Portreeve question.

Caller selects a stack directory
Client resolves its exact real path
Server validates the directory again
Registry enforces root and activation invariants
Public records return stackRoot

Intuition

The essential change is separation of concepts. Git worktrees remain useful identities for standalone services. Stack identity instead follows the directory that contains one runnable topology. Internally, stack endpoints still become ordinary claims, so the registry explicitly maps the stack root into each endpoint claim's workspace field.

Siblings: allowed

/stacks/alpha /stacks/beta

Neither root can contain the other, so ownership and discovery remain unambiguous.

Ancestor: refused

/stacks/team /stacks/team/api

These roots overlap. Portreeve refuses the second registration regardless of apply order.

Child repositories: ordinary contents

/stacks/team api/.git web/.git

Both repositories belong to the one enclosing stack; neither creates another stack identity.

Why block definition changes while live? A running activation resolves addresses from an immutable generation. If apply moved the stack to a new revision, discovery for the still-running generation would become stale. PR #14 permits the same revision idempotently but refuses changed content until the activation ends or is lost.

The public/private mapping

// Stack-facing public record
{ project: "caregiver", stackRoot: "/code/customer-stack", ... }

// Endpoint claim created for api.http
{ project: "caregiver", workspaceRoot: "/code/customer-stack",
  component: "api", endpoint: "http", transport: "tcp" }

The database column remains workspace_root. Renaming a private SQLite column would add migration risk without changing the external contract; the row mapper is the deliberate boundary.
