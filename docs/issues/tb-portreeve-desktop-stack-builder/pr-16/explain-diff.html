Portreeve · PR #16 · P4

The renderer may edit a stack without gaining a filesystem.

This change builds the trusted document boundary beneath the future stack editor. It turns a selected project directory into a narrow, evidence-checked editing capability, writes the project-owned file safely, and keeps server apply separate enough that a successful save survives a daemon failure.

Background

Why Electron has two trust zones

Portreeve Desktop renders HTML, but its renderer is deliberately sandboxed. The renderer is the place where fields, buttons, and validation summaries will live. It is not allowed to read arbitrary paths, invoke a shell, connect to the Portreeve socket, or choose an executable. The Electron main process already owns native dialogs and official-client access, so filesystem editing belongs there too.

Renderer Holds an editable definition, an opaque document UUID, and—only after a conflict—a conflict UUID. It never receives the canonical path or evidence hash.
Main process Resolves the canonical root, fixes the filename, retains baseline evidence, validates bytes and schema, and performs every filesystem operation.
Portreeve server Receives a validated definition through the official client after the file is written. It remains final authority for stack registration and live activation safety.

The project file remains authoritative

A stack is described by portreeve.stack.json at the canonical stack root. Database state is useful when a known stack has lost or damaged that file, but it is only a recovery seed. It never silently replaces a valid project file.

Key invariant: opening a document grants authority over one fixed filename at one main-process-resolved root. The renderer cannot enlarge that authority by changing a request field.

Intuition

Think of the document UUID as a coat-check ticket. It identifies trusted state that remains behind the counter; it is not the coat's storage address. The renderer can return the ticket with new JSON, but it cannot ask the attendant to visit another closet.

1. SelectMain process chooses a directory or resolves a known stack.
2. OpenRead bounded bytes and retain SHA-256 evidence privately.
3. ValidateParse the entire draft through the strict stack schema.
4. SaveCreate exclusively or replace atomically after rechecking evidence.
5. ApplyOnly verified saved content goes to the official client.

The ordering in the final two boxes matters. If Portreeve is stopped, the project's valid file still exists. The result says saved, not applied, and a later retry first confirms that those same bytes remain on disk.

The conflict is a new capability

A plain overwrite: true flag would be too broad. A stale renderer could reuse it after another editor made a second change. Instead, Portreeve returns a fresh conflict UUID bound to the exact evidence it just observed.

Open AMain process retains hash A.
External BAnother editor changes the file.
SavePortreeve refuses and returns token bound to B.
External CThe old token no longer matches current evidence.
Review CA new token is required before overwrite.

Recoverable

Missing files can be created. Malformed regular JSON can be seeded from applied state and replaced after explicit confirmation.

Refused

Symlinks, directories, other non-regular entries, and oversized files are not converted into overwrite capabilities.

Code walkthrough

1. A main-process document service

apps/desktop/main/stack-document.js is the center of the change. It canonicalizes selected directories, discovers the nearest enclosing definition, falls back to one known enclosing registered stack, and stores filename and evidence in an in-memory session keyed by a random UUID. 

sessions.set(documentId, {
  stackRoot,
  filename,
  baselineEvidence: observed.evidence,
  pendingConflict: null,
  lastSaved: null
});

2. Strict, named IPC

Shared Zod schemas define open, save, retry, issue, conflict, and mutation results. IPC accepts no arguments for native directory selection, UUIDs for known documents, and bounded content for save. Unknown fields—including a renderer-supplied path—are rejected.

3. Safe filesystem transitions

Missing files are written to a same-directory temporary file and hard-linked into place, making creation fail if another process won the race. Replacement writes and syncs a temporary file, rechecks the current evidence, and then renames atomically. The result is read again before apply.

4. Coordinator and preload integration

The existing coordinator serializes document mutations with lifecycle and refresh work, then attaches a fresh desktop snapshot. The preload publishes four fixed methods rather than a generic invoke or filesystem bridge: openStackDocument, openKnownStackDocument, saveStackDocument, and retryStackDocumentApply.

5. Tests use real files

The focused tests create actual temporary stack roots. They verify child-root resolution, two successive external edits, exclusive missing-file behavior, invalid-file recovery, safe unavailable errors, retry evidence, symlink refusal, and oversized-file refusal. Separate IPC and security tests prove that paths cannot enter through the reduced renderer API.

What this slice deliberately does not do

P4 is infrastructure beneath the editor, not the editor itself. There is no new visible Create/Edit screen in this PR. The next slices add the complete draft model, deterministic serializer, dedicated Stacks-tab editor, navigation guards, Overwrite/Cancel presentation, and visible Retry Apply state.

Portable filesystem limit: there is no ordinary cross-platform rename operation that means “replace only if the current file still has hash B.” Portreeve minimizes the remaining interval by fully preparing and syncing its temporary file, then rechecking B immediately before atomic rename.
