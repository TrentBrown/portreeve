Background

The file is the durable contract

A Portreeve stack is described by portreeve.stack.json. Its project contains components; components provide endpoints and declare dependencies on other endpoints. The file can also express automatic, preferred, or exact host-port allocation and optional Docker placement.

Earlier PRs established the server contract, filesystem safety, and an opaque main-process document capability. The missing middle was an editor-friendly representation. A form cannot simply mutate the parsed JSON object: names are both labels and reference targets, while incomplete rows must temporarily be invalid without destroying the user's work.

Intuition

Names are editable; identities are stable

Suppose website.backend points to api.default. If a developer renames api to backend, a name-based draft could leave the dependency dangling. The model instead gives the component and endpoint private local IDs and stores those IDs in the dependency.

Before rename
component-1 · “api”
endpoint-2 · “default”
dependency → component-1 / endpoint-2
→
After rename
component-1 · “backend”
endpoint-2 · “http”
serialized target → backend.http

The same identity graph makes deletion predictable. A delete request first returns the consumers and aliases that would be removed. Without explicit cascade confirmation, the original draft is returned untouched.

Invalid drafts are ordinary editing states

Adding an endpoint produces an unnamed row. That is invalid as a final file, but normal while typing. Evaluation therefore returns all issues, a filtered set for touched controls, and—on submit—the first invalid control to focus. If yesterday's draft was valid and today's keystroke is not, the preview keeps yesterday's valid JSON and marks it as stale. 

{
  valid: false,
  preview: previousValidJson,
  previewCurrent: false,
  visibleIssues: issuesForTouchedControls,
  firstInvalidControlId: "endpoint:endpoint-2:host-port"
}

Code walkthrough

1. Draft construction

createEmptyStackDraft pre-fills only the project. loadStackDraft reconstructs stable component and endpoint identities before resolving dependencies in a second pass.

2. Immutable mutation

Add, update, and delete functions clone the draft. Dependencies retain target IDs through provider renames. Delete impact is calculated before a referenced target can be removed.

3. Progressive validation

The validator mirrors schema v1 with control-specific issue IDs: trimmed unique names, booleans, port ranges, Docker coupling, valid published dependency targets, and unique local identities.

4. Two outputs

A normalized definition carries explicit schema defaults for trusted use. The preview renderer independently emits concise bytes, omitting defaults while preserving the editor's record order.

Why a custom ordered renderer?

JavaScript normally preserves object insertion order, with one important exception: integer-like property names are enumerated numerically first. A draft ordered as "10", "2", "alpha" would become "2", "10", "alpha" through ordinary JSON.stringify.

The ordered renderer operates on arrays of key/value entries, uses JSON.stringify only for individual strings and primitive values, and controls object layout itself. The result remains ordinary JSON.

Review also found that joining component and endpoint names with a delimiter could collide when that legal delimiter appeared inside a name. The final loader uses nested maps instead: component name selects one map, then endpoint name selects the ID. The regression fixture proves both ambiguous-looking pairs resolve to their intended targets and pass the authoritative schema.

Security posture

The module has no imports. It cannot read a path, contact the daemon, invoke a shell, open SQLite, or write a file. Its output is still untrusted input when P7 submits it: the main process and server independently validate the complete definition before mutation.
