Background

The larger problem

A stack is not merely a collection of unused ports. It is a topology: an API publishes an HTTP endpoint; a browser client depends on it; a worker may depend on a database or queue. Portreeve coordinates the addresses, but it deliberately does not become a process supervisor for the project itself.

Project-owned file

portreeve.stack.json describes components, endpoints, dependencies, allocation preferences, and Docker placement hints.

Portreeve authority

Canonical roots, durable assignments, generations, activations, leases, and fresh process or Docker evidence.

Project launcher

Commands, environment mapping, process and container startup, application health, shutdown, and cleanup.

A single canonical directory represents one independently runnable stack. It may be a non-Git parent containing several child repositories. Registered stack roots may be siblings, but not ancestors or descendants of each other.

What the desktop adds

The desktop Stacks tab can create and edit that same project-owned file. The renderer never receives the full path or a generic filesystem primitive. It manipulates a structured draft and sends an opaque document identifier to trusted main-process code, which performs strict parsing, exact-byte conflict detection, exclusive creation, and atomic replacement.

The important non-feature: Save and Apply does not prepare a generation or start a provider. The resulting stack details continue to say Not prepared until a launcher or developer explicitly requests preparation.

Intuition

PR #23 has two jobs. First, make every public doorway tell the same architectural story. Second, make tests stop borrowing the operating system's next ephemeral port and assuming no other development tool will ask for it a moment later.

Why the original port probe raced

Test binds port 0Kernel chooses 59353

Portreeve checkslsof sees the IDE
Correct refusalTest fails, listener survives

The failure was not evidence that Portreeve was wrong. It was evidence that the test had coupled itself to the same ephemeral allocation sequence used by Windsurf. A predictable low band was better, but VS Code Code Helper happened to select port 21060 during the same window.

The correction does not abolish the race. No probe can reserve a port after it closes. Instead, tests sample unpredictable, non-repeating candidates outside the default dynamic ranges, verify each with a real bind, and let Portreeve refuse any genuine later listener. No unrelated process is killed.

Code walkthrough

1. A shared test-only allocator

Four suites previously carried slight variations of the same Bun.serve({ port: 0 }) helper. They now import one fixture:

const firstTestPort = 10_240;
const lastTestPort = 32_767;
const attemptedPorts = new Set();

// Pick an unpredictable candidate, bind it for verification,
// skip EADDRINUSE, and never reuse it in this test process.

The range ends immediately before the default Linux dynamic range and well before the default macOS range. The real bind filters ports already owned by services. Unpredictability avoids following either the kernel's next-port pointer or another tool's obvious low-port sequence.

2. Call sites become boring

The server-client, stack CLI, operations CLI, and shared runtime fixtures all import idlePort. Removing local copies matters: any future correction now changes one test boundary rather than four subtly different ones.

3. Documentation closes the source-of-truth loop

The public guides now make these statements explicit:

  • The checked-in file owns topology, not assigned host ports.
  • Portreeve owns durable allocations, generations, activations, and evidence.
  • The client accepts an already parsed definition; the protocol has no project-file operation.
  • The desktop trusted boundary—not the sandboxed renderer—owns file discovery and mutation.
  • Apply records topology and claims; preparation and provider startup remain later, explicit actions.

4. Workflow records explain why

The approved decision records both observed listeners and rejects two dangerous shortcuts: repeatedly rerunning until timing happens to work, and killing the legitimate process that won the port. The final issue and tracker entries also connect PR #23 to the original feature rubric rather than presenting it as an isolated documentation patch.
