Background

Two kinds of truth, two kinds of authority

Already familiar with Portreeve's stack contract? Skip to Intuition.

A stack definition says what a project contains: components, their endpoints, and which endpoints other components consume. It belongs to the project as portreeve.stack.json. Portreeve's database holds a different category of information: current assignments, preparation generations, activations, evidence, and history.

Project-owned definition

Names, dependencies, publish flags, required flags, Docker service and container-port hints, and automatic/preferred/exact host-port policy.

Portreeve-owned runtime state

Which ports were assigned, whether a generation was prepared, whether a stack is active, and what listener or container evidence currently exists.

Earlier PRs established the server contract, discovery rules, trusted desktop file boundary, and a pure editor model. PR #22 connects those pieces into a user-facing workflow.

Intuition

Treat editing as a staged transaction, not a text box

A raw JSON textarea would appear simple, but it would push schema knowledge, dependency integrity, file races, and recovery decisions onto the user. The editor instead keeps an ordered draft with stable internal identities. Names can change while dependencies continue to point at the same records.

{
  "project": "caregiver",
  "components": {
    "web": {
      "endpoints": { "http": {} },
      "dependencies": {
        "api": { "target": "backend.http" }
      }
    }
  }
}

If backend is renamed to service, the dependency's internal target identity stays stable and serialization emits service.http. If the target endpoint is deleted, the editor first enumerates every affected consumer and asks whether the deletion should cascade.

Save and Apply is deliberately asymmetric. Once the file write succeeds, a daemon failure does not roll it back. The UI says “Saved, but not applied,” shows the actual error details, and offers a safe retry.

Retry is safe only when the visible draft is the definition that was saved. PR review tightened this twice: first to hide retry for dirty drafts, then to restore it when an edit is reverted exactly to the saved baseline.

Why re-rendering does not lose typing position

Every edit produces a new immutable draft and re-renders the view. Before rendering, the view captures the active text input's selection index; afterward, a microtask focuses the replacement control and restores the caret. This keeps the simple state model without making ordinary typing feel destructive.

Why preview and save cannot drift

The model's evaluation returns both preview and content from one serializer. The view displays the former and submits the latter. Invalid intermediate drafts retain the previous valid preview but label it “last valid draft,” so stale bytes are never presented as current.

Safety cases

The uncommon paths are part of the normal model

External file change

The trusted layer returns a conflict token. The renderer explains whether the file changed, appeared after open, or is invalid, and writes only after explicit Overwrite.

Missing known-stack file

The editor may seed a draft from currently applied state, clearly labels the recovery, and recreates the project file before contacting the daemon.

Invalid existing file

Nothing is partially interpreted. The user explicitly chooses a replacement draft, and the invalid bytes remain untouched until overwrite is confirmed at save time.

Daemon unavailable or refusing

The successful file write survives. Outcome, error code, message, and validation issues remain visible, and Retry Apply is scoped to the saved baseline.

Unsaved navigation

Back, Cancel, another top-level tab, and native window close all require Keep editing or Discard changes.

Live activation

The desktop cannot bypass server refusal. It surfaces the reason, leaving the written definition and current runtime state explicit rather than silently reconciling them.
