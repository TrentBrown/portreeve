Background

The release is more than a downloadable file

A PortReeve preview publishes immutable executables and disk images in a GitHub Release. It also updates two mutable discovery surfaces: the Homebrew tap tells brew which checksummed artifacts to install, while distribution/desktop-update.json tells the Desktop application which preview is available.

The old adapters updated those mutable repositories in two different ways. Homebrew cloned a repository and pushed Git directly. Desktop metadata called the GitHub contents API against main. Both could work, but neither left the same reviewable, policy-governed record as ordinary development.

Before

  • Homebrew: clone, commit, push
  • Desktop: contents API PUT to main
  • Two credential and mutation models
  • Only commit SHAs in terminal evidence

After

  • Both: exact GitHub API branch + PR
  • Merge commit only when policy permits
  • One fine-grained token model
  • PR URLs and merge SHAs in evidence
Important boundary: The release-environment approval still authorizes the exact publication plan. Generated PRs are audit and transport records; they do not silently weaken repository checks or invent a second PortReeve approval system.

Intuition

Think of the approved publication plan as a sealed shipping manifest. The GitHub Release unloads the immutable cargo first. Each mutable repository then receives its own tamper-evident delivery note: a deterministic branch and a PR whose hidden marker names the source commit, plan digest, destination, generated commit, base commit, file paths, and file checksums.

{
  "releaseVersion": "0.2.0-preview.1",
  "sourceCommit": "abc…",
  "planSha256": "def…",
  "files": [
    {"path": "Formula/portreeve.rb", "sha256": "123…"}
  ]
}

A retry does not ask “did something probably happen?” It asks “does the exact branch or PR identified by this sealed manifest exist, and do its ancestry and bytes still match?” That turns partial publication from an improvised repair into a deterministic state machine.

Absent
Create exact branch, commit, and PR.
Open and clean
Verify identity, then merge.
Open and blocked
Leave intact; report the URL.
Already merged
Verify destination and reuse.
Conflicting
Fail closed; never force-push.

Code walkthrough

1. Repository adapters become configurations

scripts/publication-adapters.js no longer contains a Homebrew clone/push or a Desktop contents-PUT path. It reads the finalized candidate bytes and supplies the shared PR publisher with an exact repository, main branch, title, source commit, plan digest, and allowlisted files.

  • Homebrew may change only Formula/portreeve.rb and Casks/portreeve-app.rb.
  • PortReeve may change only distribution/desktop-update.json.

2. Orchestration validates each result before continuing

scripts/publish-release.js passes the exact plan digest into both PRs. It validates each surface's returned evidence immediately, so malformed Homebrew provenance cannot allow Desktop publication to begin. The record remains publication-approved until every surface has succeeded.

3. Terminal evidence distinguishes new transport from real history

New approvals carry transport: github-pull-request-v1. That discriminator makes PR URLs mandatory for new completion evidence while allowing the already-completed first preview to remain exactly as it happened.

No invented history: a completed legacy record without PR URLs remains readable. A partially approved legacy record cannot silently resume through the new transport; the operator must prepare a new candidate.

The new publication-complete.json uses schema version 2 and includes the release URL, tag, both PR URLs, both merge commits, plan digest, and publication time. Release-record validation also requires the summary publication object to be deeply equal to its terminal stage evidence.

4. Hosted authority and operator guidance match

The workflow remains globally read-only. Only the release-publication job declares contents: write and pull-requests: write, and only that job receives the fine-grained token. The runbook and project skill now explain automatic merge, independent-review fallback, safe retry, branch cleanup, and the absence of ordinary Git credentials.

What recovery looks like

Suppose the GitHub Release and Homebrew PR merge successfully, but Desktop publication is interrupted. The local record remains approved rather than published. On retry:

  1. The immutable GitHub Release is byte-verified and reused.
  2. The deterministic Homebrew PR is found, its merge commit and destination bytes are verified, and no duplicate PR is created.
  3. The Desktop PR is created or recovered and merged when policy permits.
  4. Only then are complete terminal evidence and the completion document written.

If checks or an independent reviewer are required, the publisher returns an actionable error containing the exact PR URL. It does not self-approve, bypass protection, close the PR, or delete its branch.
