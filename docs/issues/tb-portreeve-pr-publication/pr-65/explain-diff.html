A safe carrier for release references

This first slice does not publish a release. It builds and proves the small state machine that future releases will use to carry exact generated files through ordinary GitHub pull requests.

Background

A PortReeve release contains immutable binaries hosted by GitHub Releases and mutable references in two repositories: a Homebrew formula/cask and the Desktop update catalog. The first public preview proved the binary side, then exposed an awkward repository side. One adapter attempted an ordinary Git push to main; another wrote directly to main through an API.

The distinction: release assets are permanent bytes. Formulae and update catalogs are moving references to those bytes. They need audit history and branch-policy compatibility without becoming a second build.

The approved design keeps main as the sole integration branch and release tags as production identity. A short-lived tb-* branch is merely a carrier for one mechanically generated PR.

Intuition

Think of the approved publication plan as a sealed shipping manifest. The new state machine constructs a crate whose label includes the manifest digest, source commit, destination, and checksum of every file. Before merging the crate, it checks the label, contents, route, and destination again.

Approved planVersion, source SHA, exact artifact digests
→
One generated commitExact allowlisted files on a deterministic tb-* branch
→
Self-identifying PRReadable summary plus machine-verifiable marker
→
Verified mergeMerge commit retained by main; exact destination bytes

For release 0.2.0-preview.1, the branch name is stable and collision-resistant:

tb-portreeve-release-v0.2.0-preview.1-<8-character version digest>

The human-readable PR body is also a signed-shaped envelope: it carries no credential, but it does carry enough exact identity to reject a branch or PR that was edited between retries.

The recovery states

Absent

Create one tree, one commit, one branch, and one PR from the current destination base.

Open

Revalidate marker, head, ancestry, paths, and bytes. Merge only when GitHub reports a clean state.

Merged

Verify the merge commit remains in destination history and every destination byte still matches.

Blocked

Keep the exact PR intact and return its URL for checks or independent review.

Conflicting

Refuse changed ancestry, extra files, modified content, changed head, closed-unmerged PR, or unproven matching bytes.

Cleanup pending

If deletion fails after merge, retry verifies public content first and removes only the unchanged topic ref.

Code walkthrough

1. Identity rendering

publicationBranchName, renderPublicationPullRequestBody, and its parser turn the version and approved plan into deterministic public identity. The marker is Base64URL-encoded JSON so recovery compares structured facts rather than scraping prose.

2. Atomic branch creation

The adapter creates a Git tree from the destination tree, then one commit with exactly one parent, then a ref. It never exposes a half-written two-file Homebrew branch and never updates main.

3. Exact validation

Validation proves the generated commit is exactly one commit ahead of its recorded base, that the base remains in destination history, that branch contents hash correctly, and that the PR reports exactly the allowed paths.

4. Policy-aware merge

Unknown mergeability receives a bounded wait. Only mergeable=true and mergeable_state=clean permit a merge request. Blocked checks, review, hooks, conflicts, or an outdated required branch return an actionable PR URL.

5. Destination proof and cleanup

After merging, the adapter proves the merge commit remains an ancestor of the destination head and rereads every file from that head. It deletes the short-lived ref only when the ref still points to the generated commit.

Safety boundaries

  • No direct commit or push to main.
  • No force-push and no administrative branch-rule bypass.
  • No self-approval or automatic weakening of required review.
  • No acceptance of matching destination bytes without a matching publication PR.
  • No branch deletion after its head changes.
  • No live publication in this slice; GitHub responses are deterministic fakes.
Why stop before wiring? The release orchestrator will coordinate an immutable Release plus two repository PRs. Reviewing this state machine first makes its invariants visible before that larger sequence depends on them.
