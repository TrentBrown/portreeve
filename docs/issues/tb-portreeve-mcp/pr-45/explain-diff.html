The bridge can now coordinate work without surrendering credentials

This slice turns the MCP bridge from an observer into a safe coordinator for standalone leases and stack activations. The central trick is to let an agent hold a useful reference without ever seeing the token that grants authority.

Background

PortReeve separates durable coordination from project lifecycle. The daemon owns claims, generations, activations, live evidence, and a SQLite registry. A project tool still starts the actual web server or container. The MCP bridge is an adapter: an agent talks MCP over standard input and output, while the bridge talks the same private Unix-socket HTTP/JSON protocol used by the official JavaScript client.

Agent host
Calls focused MCP tools. It may retain safe handles and IDs.
→
stdio bridge
Owns volatile credentials, retry memory, and bounded renewal.
→
PortReeve daemon
Owns durable truth and fresh listener or Docker evidence.

The two-phase allocation protocol exists because choosing a port and binding it are separate events. Acquire reserves a candidate briefly. The service binds it. Confirm asks PortReeve to inspect the operating system and prove that the expected process tree or Docker container really owns it.

AcquireDaemon returns a port, lease ID, short expiry, and one-time token.
BindThe project tool starts the provider on the selected port.
ConfirmFresh evidence turns the pending lease into a durable run.
ReleaseThe run ends while a sticky claim may retain its preferred assignment.
The security problem: an MCP tool must preserve the token across acquire and confirm, possibly for minutes, but returning it in structured content would place it in model context, transcripts, host logs, and perhaps durable configuration.

Intuition

Think of the bridge as a coat-check desk. The daemon gives the bridge a coat—the raw token. The bridge returns a random claim ticket—the credential handle. The ticket is useful only at that particular desk, during that desk's lifetime. Another bridge has no shared vault and therefore cannot redeem it.

Never model-visible

leaseToken stays in bridge memory and socket request arguments. It is omitted from every MCP output schema.

Safe reference

A 256-bit base64url handle identifies the in-memory record. Generic failures do not reveal whether it existed.

Durable truth elsewhere

The daemon persists only token hashes and safe history. If the bridge disappears, normal expiry recovers the port.

Bounded custody, not indefinite keepalive

A pending lease has a short TTL. The bridge renews by the earlier of one-third of the observed remaining TTL or ten seconds. Custody ends after ten minutes unless activation custody is explicitly extended, and it can never exceed sixty minutes from acquisition.

remaining lease TTL = 15 seconds
one third            = 5 seconds
maximum delay        = 10 seconds
next renewal         = min(5, 10) = 5 seconds

Confirm, skip, or abandon settles credentials immediately. One transition may settle siblings: abandoning a required endpoint can atomically cancel every remaining endpoint lease. The bridge therefore reconciles the whole returned activation, not merely the handle submitted in the call.

Retry memory is separate from credential memory

After confirmation, the raw credential must disappear—but a host may retry because the first response was lost. The bridge therefore keeps a bounded cache of safe achieved results. Equivalent normalized inputs return the prior result with changed: false. The secret is not retained merely to support replay.

Code walkthrough

1. A standalone lease can now be renewed through the public contract

The protocol adds POST /v1/leases/{leaseId}/renew. The allocation service applies the configured TTL, and the registry verifies that the lease is pending, unexpired, and paired with the correct token before updating it. History records the lease ID and new expiration, never the token. The official client exposes the same operation as renewLease.

2. CredentialCustody owns volatile authority

src/mcp/credential-custody.js groups either one standalone lease or all pending leases for an activation. It creates handles, schedules renewal, updates observed expirations, supports bounded activation extension, removes settled records, and clears everything on close. Group insertion is atomic: even a synthetic handle collision rolls back previously inserted siblings.

3. The bridge registers twelve ordinary mutation tools

Standalone

Acquire, confirm, abandon, and run release.

Stack setup

Status, prepare, activation begin, custody extension, and address resolution.

Endpoint lifecycle

Process or Docker confirm, optional skip, abandon, reconcile, and end.

Together with the fifteen earlier read tools and two new coordination reads, the bridge now exposes 29 tools: 17 reads and 12 idempotent ordinary mutations. Consequential administrative changes remain behind the later receipt slice.

4. Tests cross the real boundaries

The test suite does more than call the vault in isolation. A real PortReeve daemon and real stdio bridge coordinate a three-endpoint stack. One endpoint binds and confirms against fresh process evidence, one is skipped, and one is abandoned. The test replays calls, tries a handle through a second bridge, closes the owning bridge with a live pending lease, waits for daemon expiry, and reacquires the port.

Edge cases worth remembering

  • A bridge run ID and label are diagnostic attribution, never ownership evidence.
  • A handle from a dead bridge is intentionally unrecoverable; a later bridge inspects durable state and reconciles it.
  • Renewal errors do not disclose token material. Once the observed lease expires, the vault erases the group rather than spinning.
  • Equivalent activation-begin retries return only handles still in custody and refresh the durable activation record.
  • The bridge still never starts a service, invokes Docker Compose, opens the database, or creates a network MCP listener.
