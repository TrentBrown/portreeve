Background

PortReeve already has the hard part: a per-user daemon owns SQLite state and coordinates claims, short leases, confirmed runs, stacks, activations, Docker evidence, and launcher operations. Clients reach it through a private Unix socket carrying HTTP/JSON. The new MCP process must remain a client of that daemon, not become a second authority.

Before a bridge can register tools, it needs contracts that ordinary CLI calls did not require: every collection must page, every automated mutation needs attribution, consequential work needs evidence-bound preview and replay, and tool names must not drift between implementation slices.

Intuition

A cursor is a bookmark

A cursor encodes only the last event's timestamp and ID. It says where to continue; it grants no right to read or mutate anything.

An origin is a luggage tag

{ kind: "mcp", runId, label } helps history explain who initiated work. It is never proof of ownership.

A receipt is a sealed proposal

It binds action + target + evidence for five minutes. The result is retained so a lost response can be replayed without repeating the effect.

Why the extra executing state?

pending --atomic claim--> executing --effect succeeds--> completed
   ^                          |
   +------ effect fails ------+

second executor during "executing" => receipt_in_progress
retry after "completed"             => recorded result

Without the middle state, two independent agents could read the same pending row and both kill, delete, or rewrite. SQLite's immediate transaction admits exactly one executor before the external effect begins.

Important boundary: this slice builds the generic safety machinery. Slice I-4 will connect it to reclaim, claim, stack, document, and setting operations after each operation can collect and revalidate the right fresh evidence.

Code walkthrough

1. Freeze the surface and runtime

@modelcontextprotocol/server@2.0.0 is an exact runtime dependency. src/mcp/catalog.js freezes 51 operation-specific names, marks receipt-bound and credential-custody operations, and lists exclusions such as unsafe eviction, shell execution, HTTP MCP, resources, and prompts.

2. Page history without breaking the CLI

The daemon returns newest-first pages of 50 by default and at most 200. The official client's new historyPage exposes that directly. Existing history follows as many pages as requested and reverses the result back to chronological order, so CLI output stays familiar.

3. Carry diagnostic origin through mutations

The compatibility envelope accepts a strict origin. Request-local async context lets all registry history emitted by one mutation inherit it without threading an argument through every domain method. Tests prove an MCP-labeled client writes that label to the resulting history event.

4. Migrate durable state

Schema migration 8 adds the history origin column, a stable history-order index, and the action receipt table. Receipt rows constrain valid pending, executing, and completed shapes at the database layer.

5. Preserve trust boundaries

The SDK is not imported by the daemon. No HTTP MCP listener appears. No raw lease token or launcher credential is added to receipts or history. No unsafe-any-owner operation appears in the catalog.
