PortReeve PR #77

Keeping one Apple request attached to one exact DMG

This correction teaches the protected release producer to treat notarization as a durable conversation: submit once, remember the UUID, poll that UUID, and preserve the exact bytes Apple received if anything later fails.

Background

The broad picture

macOS distribution outside the App Store usually combines three distinct operations. Developer ID signing identifies who produced the application. Notarization sends a finished artifact to Apple for automated analysis. Stapling attaches Apple's accepted ticket to a distributable copy so Gatekeeper can verify it without relying solely on a network lookup.

Those operations do not have the same byte behavior. Submission reads a fixed DMG. Stapling later mutates a copy of that DMG by adding the ticket. A safe release system therefore needs to distinguish the bytes submitted to Apple from the final stapled bytes delivered to users.

The PortReeve boundary

PortReeve builds separate ARM64 and Intel DMGs. Only a protected, main-only job receives Apple credentials. That job cannot publish. Native verification and public publication happen later, under separate authority. PR 77 keeps those boundaries intact; it changes only how the protected producer records and survives notarization.

The observed failure

Preview 0.1.0-preview.5 reached Apple's service. The asynchronous submit response contained a valid request UUID and a success message, but no status. The producer required both fields immediately, threw an error, and deleted its temporary output before polling.

Why preview .5 is burned: the old job did not retain enough evidence to prove which exact signed bytes belong to the request. Recreating and signing a DMG may produce different bytes, so reusing the version would weaken immutability.

Core intuition

A submit response and an info response answer different questions. Submit establishes request identity. Info establishes current status. PR 77 gives each parser the strictness appropriate to its role.

Submit

Identity first

A valid UUID is enough to record request creation. Status may be absent because processing is asynchronous.

{
  "id": "11111111-2222-4333-8444-555555555555",
  "message": "Successfully uploaded file"
}
Info

Status authority

Polling must contain both the same UUID and one supported status. Missing or malformed status stops safely.

{
  "id": "11111111-2222-4333-8444-555555555555",
  "status": "Accepted"
}

The governing invariant is simple: once currentRequestId is non-null, the only legal network action is notarytool info for that exact value. A retry cannot silently create a second Apple request.

Recovery states

Each persisted record is bound to {releaseId, sha256}. A changed SHA cannot borrow an old UUID or preview identity.

Code walkthrough

1. Parse submit and info separately

parseNotarytoolSubmissionFacts accepts a valid UUID before status exists. parseNotarytoolFacts remains strict for info. Unsupported values do not become guessed defaults.

2. Drive the real producer through recovery state

notarizeDmg now creates or receives candidate-bound recovery state, persists it atomically, submits at most once, and loops through explicit actions. If a command exits nonzero but returned a valid machine-readable UUID, that UUID is salvaged and stored before the function fails.

3. Preserve submitted and delivered bytes distinctly

The producer copies the signed pre-staple DMG into recovery/candidates and submits that immutable copy. Stapling, Gatekeeper assessment, mounted verification, and final staging operate on the working DMG. If later work fails, the recovery artifact still contains the exact SHA named by the request record.

4. Retain evidence only on failure

The workflow uploads trusted-recovery-<version>-<attempt> only when the protected job fails. It has seven-day retention and contains candidate DMGs plus sanitized JSON—not the P12, P8, certificate password, keychain, or publication token.

5. Prove the negative paths

The tests cover a UUID-only submit response, two polls of one UUID, malformed info, recovery without resubmission, UUID salvage after a nonzero submit exit, and the pre-staple/post-staple byte split. The pinned repository gate passes 577 tests.

Safety boundaries that do not change

  • Apple credentials remain in the protected release-trust job.
  • The producer still runs only from a reviewed commit on main.
  • The trust job has no authority to publish a release or update Homebrew.
  • ARM64 and Intel remain separate DMGs and separate native evidence authorities.
  • A changed artifact consumes the next unused preview version.
  • Preview .5 remains a recorded failed attempt; it is not rewritten into success.
Next proof: after PR 77 merges, preview 0.1.0-preview.6 must run with trust=true and publish=false. Only that protected run can supply the remaining live Apple and native evidence.
