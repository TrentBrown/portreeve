Background

The beginner's version: signatures, notarization, and trust

A checksum answers “are these the bytes I expected?” A Developer ID signature answers “did the holder of this Apple-issued identity authorize these bytes?” Notarization adds Apple's malware-analysis result. Stapling attaches that accepted result to the distributed package, and Gatekeeper evaluates the artifact when a user opens it.

These facts are related, but none substitutes for another. A perfectly checksummed unsigned binary is still unsigned. A signed application whose embedded CLI differs from the standalone CLI is two products wearing one version number. A notarization request that timed out is not an acceptance.

The existing PortReeve system

PortReeve already uses a release record to advance a candidate through named stages. Preparation establishes native CLI artifacts; later scripts package Desktop applications, gather evidence, finalize distribution metadata, approve publication, and publish. The important design rule is “build once”: downstream work must consume already-authoritative bytes rather than quietly rebuilding them.

The previous schema described an unsigned release world. This PR preserves those historical records, but creates a new schema for releases that must distinguish internal unsigned candidates from publicly trusted Apple output.

Intuition

The core move is to turn trust into evidence-bound transitions. A release cannot merely say “signing happened.” It must be in the right prior state, use the mode demanded by policy, refer to the exact artifacts already recorded, and carry facts that later stages can independently check.

Toy example. Suppose a record begins with four CLI artifacts: macOS ARM64, macOS x64, Linux ARM64, and Linux x64. The qualification transition must report exactly four artifacts and those exact executable targets. Claiming five, omitting Linux x64, or supplying an unrelated tarball fails before credentials are touched.

Notice the separation between trust and publication. Signing credentials live in one protected environment. Publication credentials live in another. Approval to create trusted artifacts does not authorize publishing them.

No silent compatibility trick. Schema version 1 stays readable under its original ten-stage vocabulary, but mutation APIs reject it. The code neither upgrades history in place nor pretends old unsigned previews carried new evidence.

Code walkthrough

1. Release-record schema dispatch

scripts/release-record.js now dispatches validation by schema version. New records use version 2 and the twelve stages. Legacy records retain their old vocabulary for inspection only. Every v2 transition verifies its immediate predecessor and stage-specific evidence.

policy.desktopTrust === "developer-id-notarized"
  ? authority.mode must equal "developer-id-signed"
  : authority.mode must equal "unsigned-internal"

This binding closes an important loophole found during review: a trusted policy can no longer advance by claiming unsigned authority.

2. Artifact qualification is derived, not asserted

Qualification now calculates the initial artifact set from the record. The submitted count must equal that set, and the executable members must form the exact four-target matrix. An evidence document cannot invent coverage by placing a plausible number in a field.

required targets = {
  darwin-arm64, darwin-x64,
  linux-arm64,  linux-x64
}
reported artifactCount = actual initial artifact count

3. Apple trust contract

scripts/apple-trust-contract.js centralizes the exact PortReeve Developer ID identity, Team ID, and product-specific notary profile. It parses machine-readable or stable command output into explicit facts for codesign, notarytool, stapler, and Gatekeeper rather than treating exit status alone as proof.

Its injected command runner has finite timeouts. Credential preparation records the keychain state it changed and cleanup runs after success, action failure, or preparation failure. If both the main operation and cleanup fail, an aggregate error preserves both causes.

4. Immutable notarization recovery

A notarization attempt carries a byte digest, release version, deadline, upload-attempt count, and—once Apple creates it—the request ID. A known request is polled. It is never resubmitted. Upload may be retried only when evidence proves no request exists.

5. Pipeline callers and tests

Preparation, native evidence, Desktop packaging, finalization, and publication callers now speak the v2 stage vocabulary. Tests cover successful progression as well as malformed Apple output, rejection, indeterminate status, timeout, cleanup failure, detached artifact evidence, policy mismatch, stage skipping, and attempted legacy mutation.

What remains after this slice

This PR provides the grammar and invariants, not the final Apple release. Later governed slices must produce signed per-architecture CLI bytes, wire the protected main-only producer, embed the same bytes in architecture-specific applications and DMGs, collect native ARM64 and Intel evidence, finalize every distribution surface from those bytes, and run a nonpublishing protected rehearsal.

That boundary matters: passing this PR means “the foundation is safe to build upon,” not “PortReeve is now shipping notarized releases.”
