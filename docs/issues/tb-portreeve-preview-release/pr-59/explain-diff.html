Background

The release record already identifies one source commit and four promoted CLI executables. A Desktop release must preserve that identity while adding Electron, an application bundle, a disk image, and Homebrew metadata. Rebuilding or choosing a CLI implicitly would break the build-once promise.

Each native macOS runner packages only its own architecture. It verifies the embedded CLI digest, the Electron executable architecture, application contents, and a read-only launch. It then creates a compressed DMG, mounts it, verifies the application again, and emits a create-once evidence fragment.

The key invariant: the cask does not merely point at two plausible files. Each URL and checksum is derived from two DMGs whose evidence traces back to the same release record and exact CLI digests.

The join step accepts exactly one ARM64 and one x64 fragment in canonical order. Preview releases explicitly remain unsigned; stable releases fail before writing distribution files unless Apple signing and notarization evidence is present.

Code walkthrough

1. Explicit packaging inputs

packageDesktop now takes a release directory, output root, architecture, and smoke policy. The application resolver is pointed at the exact prepared workspace instead of searching an ambient default.

2. Architecture and identity attestation

Desktop inspection checks the Electron Mach-O architecture as well as the embedded CLI architecture, digest, byte count, version contract, ASAR contents, and packaged modules.

3. DMGs are exercised, not assumed

The DMG helper creates a non-overwriting compressed image, runs hdiutil verify, mounts it at an isolated path, inspects the copied application, detaches it, and records the final byte count and SHA-256.

4. Homebrew does not own PortReeve service data

The generated cask installs the app and provides lifecycle guidance, but intentionally has no destructive zap. Removing native supervision and deleting claims, history, and settings remain explicit PortReeve operations.

5. Interrupted finalization stays deterministic

Distribution files are create-once. An identical existing cask or checksum manifest is safely reused after interruption; changed content is rejected.
