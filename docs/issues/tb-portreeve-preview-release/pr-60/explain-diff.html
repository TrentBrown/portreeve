Background

The local engine can build all CLI targets, but only matching native hosts can prove that each executable and supervised lifecycle works. Desktop packaging has the same constraint for Apple Silicon and Intel. GitHub Actions supplies those hosts; it must not become a second release implementation.

Design rule: workflow YAML supplies runners, transport, and credentials. Versioned repository scripts continue to own policy, evidence validation, stage transitions, and publication behavior.

Every job downloads the same prepared workspace. Native and Desktop jobs emit create-once fragments instead of editing shared state. One Linux join job validates the four CLI fragments; one distribution job validates the two Desktop fragments. Neither join rebuilds an artifact.

Publication is its own state transition

release:publish rereads the finalized record, rehashes every artifact, regenerates the plan, and requires the committed plan bytes to match. Without --confirm and an approver identity it stops before even calling remote preflights.

verify record + bytes
  → compare exact publication plan
  → require explicit confirmation
  → preflight GitHub, tap, and update target
  → persist plan-bound approval
  → publish or verify each remote target
  → persist published evidence

GitHub release assets are immutable by name, size, and SHA-256. The tap and update document are public moving references, so the approval plan names them explicitly. Update publication uses the repository file SHA as an optimistic concurrency guard.

If GitHub succeeds and the tap temporarily fails, the record remains publication-approved. A retry must reproduce the same plan digest, verifies the existing GitHub release, and resumes without rebuilding or replacing version assets.

No real publication occurred: tests supply fake adapters. The workflow has not been dispatched and the public token remains unused.

Update metadata no longer means “one unqualified latest”

Schema version 2 carries preview and stable entries independently. Each entry records coordinated release version, Desktop component version, product maturity, channel, trust, download page, and both architecture-specific DMG identities.

The packaged app also records and attests its selected channel. An alpha preview follows preview metadata; a future stable package follows only stable metadata. A stable entry is invalid unless maturity is stable and Desktop trust is Developer ID notarized.

npm is intentionally absent from the hosted dependency graph. The client archive remains part of prepared evidence, but npm publication stays deferred until Trusted Publishing is configured independently.
