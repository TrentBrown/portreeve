Background

PortReeve has three distinct forms that are easy to blur together. The daemon owns the durable port registry and answers the Unix-socket protocol. The standalone executable is the public CLI and the byte-for-byte artifact installed under launchd or systemd-user. The Desktop application is a management console. There is one PortReeve installation, not a separate Desktop-only server.

Daemon

Allocates ports, stores claims and stacks, and exposes the local socket protocol.

Standalone artifact

Runs the CLI and daemon. Its checksum is verified before Desktop may install or upgrade it.

Desktop

Presents evidence and named operations. Its renderer is sandboxed and cannot own native authority.

The old route

The Desktop used to spawn the verified executable for every lifecycle action, ask for JSON, buffer its output, impose an adapter timeout, parse a CLI envelope, and translate that envelope back into Desktop state. This was safe enough during early development, but it made one trusted PortReeve adapter invoke another trusted PortReeve adapter.

The child-process boundary duplicated policy. The CLI adapter owned a 10- or 30-second timeout even though the underlying native work could still be running. Failures arrived as process output rather than canonical lifecycle evidence. Cross-process locking and uncertain-outcome recovery, delivered in PR 38, made that split especially unnecessary.

Intuition

Before

  1. Spawn portreeve start --json.
  2. Wait for stdout and an exit code.
  3. Parse the CLI envelope.
  4. Re-validate the nested result.
→

After

  1. Call LifecycleService.start().
  2. Validate the canonical result.
  3. Reduce it for the renderer.
  4. Keep the verified artifact for installation.
The key separation: the Desktop embeds lifecycle control logic, but it does not install that embedded JavaScript as the server. It still promotes the checksum-verified standalone executable.

A toy example

Suppose the Desktop controller is PortReeve 0.1.0 and the verified artifact manifest also says 0.1.0. A Start click goes directly to the shared service. The service acquires the global lifecycle lease, gathers before-evidence, performs native work, gathers after-evidence, and returns one validated result.

Code walkthrough

1. One fixed controller

apps/desktop/main/lifecycle-controller.js receives the already verified artifact and the embedded PORTREEVE_VERSION. Production startup supplies no home, socket, supervisor, environment, or arguments. The controller creates the shared service with only this installation source: 

createLifecycleService({
  sourceExecutable: artifact.executablePath
})

Status, all six lifecycle mutations, purge preview, and purge execution call the service directly. The controller still validates each returned value against the canonical schemas; direct calls do not mean unchecked calls.

2. Exact identity, fail closed

The PortReeve controller version must exactly equal the artifact manifest version. Desktop's own application version is deliberately separate. A mismatch creates a stable controller_artifact_version_mismatch error. Every mutation checks it before service entry. 

controller 0.1.0 + artifact 0.1.0 → mutations enabled
controller 0.1.0 + artifact 0.2.0 → reads available, mutations disabled

3. Minimal renderer evidence

The strict Desktop snapshot adds only controller version, a mutation-enabled boolean, and a safe error. It does not reveal the executable path or permit the renderer to choose it. Schema refinement rejects contradictory states such as “enabled with an error.”

Visible

Controller version, mutation state, stable mismatch code and message.

Main only

Executable path, purge token, default home/socket, native supervisor and arguments.

4. The old subprocess implementation disappears

The PR deletes cli-adapter.js and its subprocess-oriented tests. Security coverage now asserts that the Electron entry and controller contain no child_process, spawn, or CLI fallback. Native supervisor helpers may still execute launchctl or systemctl inside the shared lifecycle implementation; what disappeared is the Desktop spawning PortReeve's CLI as its API.

5. Tests stop seeing the developer's real service

A full test run while the legitimate global launchd agent was active exposed an old fixture flaw. Temporary data and socket paths were paired with the real global supervisor label. The tests now inject unique launchd labels and systemd units, so a local PortReeve installation can keep running throughout the suite.

Safety cases

Matching versions

All named lifecycle operations enter the shared service. Existing lock, deadline, rollback, recovery, and no-downgrade policy applies.

Mismatched versions

Desktop opens, explains the mismatch, hides native lifecycle buttons, and refuses direct IPC mutation attempts before service entry.

Purge

Preview remains readable. Its secret token stays in main and is single-use. On mismatch the dialog becomes preview-only and execution remains blocked in depth.

Newer installed service

Matching controller/artifact identity does not authorize downgrade. The shared manager still compares installed and running versions and refuses replacement.
