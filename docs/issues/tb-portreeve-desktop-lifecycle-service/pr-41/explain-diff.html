PortReeve PR #41

Proving what we actually ship

The Desktop had already stopped delegating lifecycle work to the CLI. This slice closes the verification gap: it proves that the packaged application contains the direct controller, embeds the exact release artifact, behaves identically under Bun and Electron Node, and can start safely as a real .app.

Background Intuition Code Quiz

Background

PortReeve has two different executable concerns. The standalone CLI binary is the public command-line product and the byte sequence that lifecycle installation promotes into the managed location. The Electron main process, however, should call the shared JavaScript lifecycle service directly. It must not launch that binary merely to ask it to perform lifecycle work.

Retired delegation

Desktop → CLI → service

Electron spawned the CLI, parsed JSON, and owned timeout and output handling.

Current authority

Desktop → shared service

Electron constructs a fixed controller in process. The verified binary is only the installation payload.

Source-level tests established that architecture in earlier slices. Packaging introduces a different question: did the build really put those exact pieces into app.asar, beside the intended manifest-selected executable? A green unit test cannot answer that by itself.

A useful distinction: “no lifecycle CLI spawning” does not mean “no child processes.” The shared lifecycle service still has legitimate reasons to invoke launchctl, systemctl, lsof, and related native tools. The forbidden behavior is delegating the lifecycle operation back through the PortReeve CLI adapter.

Intuition: three seals on one package

Think of packaging as sealing a crate. We check the inventory before closing it, inspect the closed crate, and finally operate the delivered product in a harmless mode.

1. Before
module graph and version agreement
2. Assemble
ASAR plus release resources
3. After
checksum, metadata, and bundle inspection
4. Run
real app, isolated read-only status

Toy example

Suppose the source controller says 0.1.0 but a stale release directory contains 0.0.9.

controllerVersion = 0.1.0
desktopVersion    = 0.1.0
artifactVersion   = 0.0.9

result: package fails before Electron Packager runs

If all three versions agree, the build records a small attestation in the ASAR. The post-package check independently opens the archive, re-reads that attestation and package metadata, validates the embedded manifest and SHA-256 checksum, and checks the main bundle for direct controller markers and retired adapter markers.

Composition

Code walkthrough

1. Packaging becomes a verification pipeline

scripts/package-desktop.js requests Bun's build metafile, verifies the source-module graph, selects the release artifact through the existing checksum-aware resolver, and refuses any version drift. It writes a compact desktop-verification.json into the staged application before Electron Packager assembles the ASAR.

2. The assembled application is inspected

scripts/desktop-package-lib.js uses the build-only @electron/asar dependency to require the package document, attestation, and main bundle. It also resolves the executable from the packaged release manifest, checking its safe filename and SHA-256 checksum through the same artifact resolver used at application startup.

3. One contract runs in two JavaScript worlds

test/desktop/runtime-contract.js is deliberately ordinary JavaScript. It constructs the controller with a fake canonical service, exercises status, all six ordinary lifecycle mutations, manual stop, and evidence-bound purge, then verifies exact installation provenance. The runner executes the same file once with pinned Bun and once with Electron using ELECTRON_RUN_AS_NODE=1.

4. The real app gets a harmless smoke entrance

When the private packaging flag is present, Electron main resolves the packaged artifact, constructs the fixed controller, calls only status(), prints a bounded identity marker, and quits. The packaging harness supplies temporary home, state, socket, supervisor, and Electron user-data paths. The branch returns before creating the PortReeve client, launcher runtime, IPC handlers, or browser window.

This smoke proves startup and read-only integration. It intentionally does not claim to prove install, restart, interruption, or close protection. Those native mutations belong to the final P7 slice.
