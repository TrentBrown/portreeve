Background

The beginner’s version

PortReeve has two kinds of work. The everyday server allocates and describes ports. Lifecycle administration installs that server, asks the operating system to supervise it, starts or stops it, and can remove its data. Those administrative actions touch the filesystem, launchd or systemd, a Unix socket, and a process that may be starting or stopping at the same time.

Before this feature, the CLI had already been reduced to a presentation adapter around a shared lifecycle service. PR 38 gives that service two missing safety properties:

Time

Every layer is bounded

Native commands, readiness polling, complete mutations, reads, and recovery observations all have finite budgets.

Exclusion

Only one mutation enters

A live per-user Unix listener is the lease. Another CLI or Desktop process receives lifecycle_busy promptly.

Evidence

Failure is re-observed

If a deadline expires after work may have begun, PortReeve gathers fresh status and reports partial or failed.

The narrower problem

Lifecycle work crosses process boundaries. Suppose one CLI asks launchd to start PortReeve while the Desktop asks system state to uninstall it. Each caller might have correct local logic, yet the interleaving is nonsensical. Likewise, rejecting a UI promise after fifteen seconds does not stop an in-process command or rollback. The shared service must own both serialization and time.

Core intuition

The important inversion: a timeout is not the caller giving up. It is the lifecycle engine ending bounded work, then asking the host what is true now.

The listener lease is deliberately not a PID file. Binding a Unix socket is atomic. Connecting to it is fresh proof that an owner is alive. PID, operation, UID, and acquisition time travel over that connection only as diagnostics. If the owner crashes, the kernel drops the listener; a refused connection plus safe socket ownership/type evidence permits recovery.

One protected transaction

Caller
Requests start, stop, restart, install, uninstall, manual stop, or purge.
Service
Starts the overall deadline and atomically binds the mutation-listener path.
Service
Collects validated before-evidence while holding the lease.
Manager
Runs bounded native commands and bounded readiness waits using the same deadline signal.
Service
Collects after-evidence. On error or expiry, it uses a separate bounded recovery observation.
Service
Returns one canonical result, then closes accepted peers and releases the listener.

Status and purge preview skip the lease. They are finite reads, so they remain available while another process mutates the installation.

Purge detail: the mutation listener lives in the per-user runtime directory, outside the marker-owned application home. Complete purge may delete PortReeve data, but it cannot delete the lock that protects that very purge.

What timeout means

LayerDefault budgetWhat happens at expiry
Native control command15 secondsThe control subprocess is hard-stopped; the surrounding mutation becomes uncertain and is re-observed.

Complete mutation60 secondsThe AbortSignal reaches child work and socket probes; recovery status starts afterward.
Status / purge preview15 secondsThe read terminates without taking the mutation lease.
Recovery evidence10 secondsFresh host state determines failed versus partial; PortReeve never fabricates success.

Toy example

before: supervisor=inactive, socket=unavailable
action: launchd accepts start, but health wait expires
after:  supervisor=active, socket=unavailable

result:
  code: lifecycle_timeout
  outcome: partial
  changed: true

If after-evidence equals before-evidence, the outcome is failed. Purge now has that same vocabulary; calling an unchanged timeout “partial” would falsely claim that evidence changed.

Code walkthrough

1. Deadline policy

src/supervision/deadline.js centralizes budgets, expiration, command options, and referenced intentional waits. The overall timer itself is unreferenced so an unused deadline cannot keep a process alive; an awaited lifecycle sleep remains referenced so foreground Node does not exit mid-operation.

2. Process-safe lease

src/supervision/lock.js binds a private Unix socket. It probes an existing listener, refuses live owners, and only removes an abandoned path when it is a same-owner socket rather than a symlink or regular file. Release stops new connections and destroys accepted peers before awaiting server close.

3. Service transaction

src/supervision/service.js wraps every mutation and purge. The lease surrounds before-evidence, mutation, rollback performed below the service, after/recovery evidence, and canonical result creation. Busy is a refusal; other unchanged errors fail; changed evidence is partial.

4. Propagation through existing mechanisms

The manager, launchd adapter, and systemd-user adapter accept the shared context. Native commands receive the remaining budget and AbortSignal. The official client adds optional signals only to health and protected stop requests, preserving every existing call.

5. Adapter compatibility

The CLI still maps stable service codes to old exit bands: busy remains conflict (20), while lifecycle timeout remains internal (70). Desktop schemas temporarily accept purge’s new failed outcome; the next slice replaces the Desktop CLI subprocess adapter with this service directly.

Edges and compatibility

  • A regular file, symlink, or foreign-owner object at the lock path is never removed. PortReeve fails closed.
  • Twelve concurrent processes racing to recover a killed owner produce exactly one lease winner in the integration test.
  • A connected peer cannot indefinitely delay release.
  • A native command that ignores SIGTERM is still bounded because the expired control subprocess receives SIGKILL.
  • No registry schema, daemon endpoint, supervisor definition, command name, or existing JavaScript call signature is removed.

Remaining release gates are intentionally elsewhere: real Linux systemd-user operation, full real macOS mutation, packaged Electron execution, close protection, and forced-interruption recovery.
