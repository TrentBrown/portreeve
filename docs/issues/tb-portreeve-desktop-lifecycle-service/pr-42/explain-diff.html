Check your understanding

1. Why is PID metadata not used to reclaim the lifecycle lock?

PIDs can be stale or reused. PortReeve probes the Unix listener for fresh ownership evidence; a refused connection identifies an abandoned socket artifact.

2. What can still run while a mutation owns the lifecycle lease?

Read-only status and purge preview remain available. Another mutation is refused promptly with lifecycle_busy.

3. Why not test native mutations through a hidden packaged-app switch?

That would ship extra privileged authority solely for tests. The isolated native release matrix already exercises real launchd/systemd-user mutations safely.

4. What happens when a lifecycle operation times out after mutation may have begun?

The service gathers bounded fresh after-evidence and returns a canonical timed-out partial or failed result; an adapter cannot label it cancelled simply because it stopped waiting.

5. Is the standalone PortReeve executable obsolete after this refactor?

No. It remains the public CLI, the installed daemon payload, and the future MCP entry point. Only Desktop lifecycle orchestration moved from spawning it to calling the shared service in process.
