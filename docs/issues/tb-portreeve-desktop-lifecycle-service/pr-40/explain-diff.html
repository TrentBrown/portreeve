Background

PortReeve Desktop does not merely edit preferences. Its main process can install an executable, create or remove native supervision, start and stop the server, and purge service data. Earlier slices moved these operations out of a spawned CLI and into the same lifecycle service used by the CLI. That gave both entry points one definition of success, refusal, partial completion, and failure.

Renderer
Displays evidence and asks for a named action. It is not trusted with paths or native arguments.
Preload
Allows a narrow API across Electron context isolation and validates returned data.
Electron main
Owns the controller, lifecycle activity, close decision, and safe reduction.
Host
launchd or systemd-user, files, socket evidence, and the managed PortReeve process.

Two gaps remained. First, a user could normally close the application while a trusted mutation was in flight. Second, the old failure view either said too little or retained bounded native output—which can still contain a secret, command argument, or private path.

Why “bounded output” is not “safe output.” A 2 KB stderr tail is small, but it can still contain TOKEN=…, a complete invocation, or a home-directory path. The safe boundary must select fields, not merely truncate bytes.

Intuition

One main-process fact drives two presentations

When a lifecycle mutation is accepted, the coordinator immediately records a small fact such as { operation: "restart", startedAt: "…" }. The same fact drives the visible activity notice and the close guard. The renderer may display it, but it cannot clear it or approve a close.

1
Renderer requests Restart.
No executable, path, environment, or supervisor is supplied.
2
Main records active = restart.
Subscribers receive the strict activity event immediately.
3
A close attempt asks main again.
BrowserWindow close and Command-Q both call applicationCloseState().
4
The service settles and refreshes evidence.
Only then is activity cleared and normal close allowed.

Diagnostics are a projection, not a copy

A thrown object might contain dangerous material:

{
  code: "lifecycle_unavailable",
  output: "TOKEN=top-secret",
  arguments: ["--home", "/private/path"],
  stack: "Error … /private/path/file.js"
}

The renderer receives only an approved projection:

{
  "operation": "start",
  "layer": "start",
  "outcome": "failed",
  "code": "lifecycle_unavailable",
  "message": "The lifecycle operation is currently unavailable; refresh host evidence before retrying.",
  "timedOut": false,
  "nativeExitCode": 70,
  "before": null,
  "after": null,
  "recovery": ["Refresh PortReeve status to gather fresh host evidence, then retry the operation."]
}

Code walkthrough

1. Coordinator activity and final refresh

mutate(work, lifecycleOperation) distinguishes lifecycle mutations from other serialized desktop work. Install-and-start, start, stop, manual stop, restart, upgrade, uninstall, and purge execution supply a name. Purge preview deliberately does not. Existing result paths still call collect() before returning their final snapshot.

2. Window close and application quit share authority

The former launcher-only close state is now composed in the coordinator. bindWindowCloseGuard covers the BrowserWindow event, while the new bindApplicationCloseGuard covers Command-Q and other before-quit paths. Both prevent the event before notifying the renderer.

3. Separate launcher and application schemas

An attached launcher still has its original reduced close state. The application state extends it with nullable lifecycle activity. Keeping the schemas distinct avoids pretending that a launcher process group and a native lifecycle mutation are the same thing.

4. Two strict validation layers

BoundaryMechanismWhat it prevents
Electron mainStrict Zod schemas and allowlisted error reductionArbitrary exceptions cannot become renderer result fields.
PreloadExact-key and enum validationAn extra output, path, or credentials field is rejected.
RenderertextContent and JSON in a preDiagnostic strings cannot become executable markup.

5. A developer-facing failure view

The last-operation card keeps its concise summary and evidence list. On failure it adds an expandable “Diagnostic packet” section and a copy button. Close attempts during mutation show the exact operation and explicitly say it cannot be cancelled safely. Launcher termination controls are hidden in that state because they solve a different problem.

Edge cases and preserved behavior

Purge preview

It remains serialized with desktop work but does not set lifecycle activity, so it does not block close.

Command-Q

It may bypass a window-first path, so the application before-quit event has its own guard.

Force quit

The OS can still terminate the app. The next launch must use fresh host evidence; that native interruption proof belongs to I-6.

Unknown error code

It is reduced to internal and a fixed message rather than echoed into the renderer.

The PR does not make the renderer a lifecycle controller, invent a cancel protocol, change CLI output, alter PortReeve's daemon protocol, or treat a stored PID as authority.
