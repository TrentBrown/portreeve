One lifecycle authority, beginning with the CLI

PortReeve already knew how to install and supervise its server. This change moves the meaning of a lifecycle operation out of the command-line interface and into a reusable internal service—the foundation the Desktop app can call directly in a later slice.

Background Intuition Code Quiz

Background

Mechanism and meaning had become entangled

PortReeve runs a per-user server under the operating system's native supervisor: launchd on macOS and systemd-user on Linux. The existing LifecycleManager performs the mechanism work—copying and validating the standalone executable, talking to the supervisor, checking the Unix socket, rolling back failed upgrades, and purging managed data.

Before this PR, the CLI command module also decided what an operation meant. It gathered status before a mutation, called the manager, gathered status afterward, classified the result, and chose an exit code. That was acceptable while the CLI was the only trusted caller. It became a problem when the Desktop app needed the same behavior without treating a child CLI process as an API.

CLI command Orchestrates, classifies, renders, and exits
→
LifecycleManager Filesystem, supervisor, socket, rollback, and purge mechanisms
→
Operating system launchd or systemd-user plus the running server
The duplication risk: if Electron copied the CLI's orchestration, the two callers could eventually disagree about whether a timeout was a failure, a partial change, or a refusal. If Electron kept spawning the CLI, errors and state crossed a fragile text/subprocess boundary.

The contracts that must survive the refactor

The CLI is already a public product. Its command names, JSON envelopes, human-readable meanings, exit-code bands, purge confirmation token, home and socket overrides, and no-downgrade behavior cannot casually change. Likewise, the public JavaScript client remains a client of the running PortReeve daemon; it is not the privileged local lifecycle controller.

Intuition

Return evidence first; let each adapter present it

The new internal service owns the transaction story. A mutation starts with fresh evidence, performs one manager operation, then gathers fresh evidence again. It returns one validated result. Nothing in that result says “exit code 20” or “print this sentence”; those are CLI presentation choices.

Before evidence Installation absent; supervisor unavailable; socket unavailable
→ mutate →
After evidence Installation installed; supervisor active; socket healthy 
{
  "operation": "start",
  "outcome": "succeeded",
  "changed": true,
  "startedAt": "...",
  "completedAt": "...",
  "before": { "mode": "none", "...": "..." },
  "after": { "mode": "supervised", "...": "..." },
  "error": null
}

Five terminal meanings

succeededThe requested change completed.
no-changeThe requested state already held.
refusedEvidence showed a conflict or incompatible request.
partialAn error occurred after observable state changed.
failedAn error occurred without observable state change.

Consider a start operation that invokes the supervisor and then fails a health check. If the after-evidence shows that the supervisor became active, calling the operation merely “failed” loses important recovery information. The service reports partial and includes both snapshots. If a manual server already owns the socket, the service reports refused. The CLI then maps the structured error code to its established process exit band.

CLI adapter Arguments, text/JSON rendering, exit code
→
LifecycleService Evidence, mutation transaction, canonical outcome
→
LifecycleManager Native mechanisms remain unchanged
Why begin with the CLI? Moving the existing caller first proves the new boundary while observable behavior is held constant. The Desktop can adopt the same service later without inventing a second meaning for lifecycle results.

Code walkthrough

Three responsibilities, now separated

Presentation src/cli/commands/lifecycle.js
Render output and map exit bands.
Application service src/supervision/service.js
Validate and classify lifecycle evidence.
Mechanism LifecycleManager
Existing supervisor, socket, and filesystem work.
  1. A reusable service is introduced. LifecycleService exposes status, install, uninstall, start, restart, stop, manual stop, purge preview, and purge. Every returned value is parsed through the existing Zod contract before crossing the service boundary.
  2. Mutation semantics move intact. The old CLI helper's before/after snapshots, state fingerprint, error reduction, and terminal outcome classification now live in the service. The existing manager and native implementations are not rewritten.
  3. The CLI becomes an adapter. Each command delegates to one service method. It renders the canonical result and maps result.error.code to an established exit-code band. Status and purge keep their existing CLI-specific presentation rules.
  4. Error-code mapping becomes reusable. exitCodeForErrorCode handles stable structured codes, while the older exitCodeForError continues to cover thrown Commander, Zod, and client errors.
  5. Tests lock both sides of the boundary. Service tests cover every mutation and the current outcome categories. CLI golden tests prove all six mutation JSON envelopes and exit bands remain stable. A structural guard rejects lifecycle-manager orchestration in the CLI module.

Deliberately not in this slice

This is a foundation PR, not the entire Desktop refactor. Deadlines, uncertain-outcome recovery, cross-process mutation locking, the trusted Electron controller, close protection, renderer-safe diagnostic packets, and the complete macOS/Linux packaging matrix remain explicit later issues. In particular, Electron still uses its existing CLI adapter until the shared service acquires the safety properties required of both callers.
