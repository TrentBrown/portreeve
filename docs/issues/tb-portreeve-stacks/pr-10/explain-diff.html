Trust the container evidence, not Docker’s shared PID

This change lets one stack activation mix ordinary host processes and Docker containers. Portreeve still owns endpoint identity and port allocation; the project launcher still owns Compose and container lifecycle.

Background

A Portreeve activation starts from one immutable generation: every published component endpoint already has a claim and an allocated host port. Before this PR, every endpoint was confirmed by finding a live listener and proving that it belonged to a submitted root process. That model works for Bun, Node, or any ordinary process tree.

Durable

Claim

The stable identity: project, canonical worktree, component, endpoint, and TCP.

Immutable plan

Generation

One coherent assignment of host ports for every published endpoint.

One launch attempt

Activation

Short-lived leases become confirmed process or Docker runs.

Docker breaks the process-tree proof. On macOS, lsof often shows a Docker Desktop backend. On Linux it may show a proxy or daemon-related listener. Either process can serve several containers. Killing it to reclaim one port could disrupt unrelated work.

The central constraint: a PID observed on a Docker-published port is evidence that the host port is listening, but it is not evidence of which container owns the publication.

Intuition

The solution is not to abandon lsof. It is to combine two independent views. Host listener evidence says “the allocated address is live.” Fresh Docker inspection says “this exact running container carries this activation’s identity and publishes this host port to this declared container port.” Both must agree.

1 · BeginLauncher selects api as Docker-backed.
2 · LeasePortreeve returns port, container port, service, and exact labels.
3 · LaunchLauncher applies labels and publishes only the allocated loopback port.
4 · InspectPortreeve checks running state, labels, mapping, and host listener.
5 · ConfirmOne Docker-typed run is committed transactionally.

The container ID submitted later is deliberately weak: it is only the key used for a fresh docker inspect. A stale ID cannot confirm anything by itself.

Code walkthrough

1. Provider-typed persistence

Schema migration 5 rebuilds runs with a binding_kind. A process run requires a root PID and forbids a container ID; a Docker run requires a container ID and forbids a root PID. Existing rows migrate as process runs without losing assignment or history data.

2. A small Docker adapter

DockerCliAdapter invokes the host’s configured docker CLI. It normalizes only running state, labels, and TCP publications. Inventory finds an exact host port by freshly inspecting running containers; the live smoke removed an unreliable Docker CLI publication filter.

3. Dynamic capability and mixed begin

The server advertises docker-evidence-v1 only when the Docker daemon answers at startup. A begin request may choose Docker by component; omitted components remain process-backed. Docker absence leaves process-only allocation and activations intact.

4. Two confirmation unions

// Existing shorthand remains process-backed
{ leaseId, leaseToken, rootPid }

// Docker is explicit and carries no PID
{ leaseId, leaseToken, bindingKind: "docker", containerId }

The Docker path recomputes required labels from durable stack and activation state, inspects the container, verifies 127.0.0.1:hostPort → containerPort/tcp, checks a fresh host listener, and commits the run in one registry transaction.

5. Client and CLI

The official JavaScript client still uses the same HTTP/JSON Unix socket. It preflights Docker capability for Docker-only calls. Commander adds --docker-component to begin and a separate stacks confirm-docker command so PID and container evidence cannot be accidentally mixed.

Safety cases

Fresh match

Return launcher action

Inventory returns the exact freshly observed container ID. Reclamation says launcher-action-required and emits no signals.

Docker unavailable

Refuse conservatively

If storage says the active run is Docker-backed but Docker cannot be inspected, even unsafe eviction refuses. A stored ID is not returned as fresh authority.

Docker absent at startup

Keep process paths working

The capability is omitted and Docker discovery is not attached to ordinary inventory. Process-only stacks behave as before.

Authority stays outside Portreeve: the structured action is information for the trusted launcher. Portreeve does not execute docker stop, run Compose, or assert application readiness.
