From isolated claims to a shared stack vocabulary

This change gives Portreeve a durable, declarative description of a worktree's components and endpoints—without turning Portreeve into the program that launches them.

Background

The earlier authority knew services one at a time

Before this PR, a durable port claim was identified by project, canonical worktree, service, and TCP transport. That was enough to remember that the caregiver website preferred port 3000. It was not enough to describe several endpoints on one component, nor to say that the website depends on the API's HTTP endpoint.

Before

One service-shaped claim

{ project: "caregiver",
  worktree: "/code/caregiver-a",
  service: "api",
  transport: "tcp" }
After

One canonical endpoint claim

{ project: "caregiver",
  worktree: "/code/caregiver-a",
  component: "api",
  endpoint: "http",
  transport: "tcp" }

The old word service remains accepted. Portreeve normalizes it to a same-named component and the endpoint default. Responses retain the service field as an alias, so existing callers do not have to migrate in lockstep.

Authority boundary. A stack definition describes logical topology and port intent. It contains no commands, credentials, Compose invocation, or health logic. The project launcher remains responsible for starting processes and containers.

Intuition

Think of portreeve.stack.json as a checked-in map and the SQLite registry as the local land office. Applying the map does not build the town. It records stable names, validates references, and links published endpoints to reusable port claims.

1 · DiscoverThe CLI finds the definition at the canonical worktree root.
2 · ValidateOne strict schema supplies defaults and rejects unknown or ambiguous fields.
3 · HashKeys are sorted deterministically and the normalized JSON receives a SHA-256 revision.
4 · TransactThe stack, revision, endpoint links, claims, and history change atomically.
5 · InspectCLI and client can list or show the normalized current definition.

Why a content hash?

Two files with the same meaning may order their keys differently. Hashing raw bytes would call that drift. Portreeve first materializes defaults and sorts object keys with locale-independent JavaScript ordering. Equivalent content therefore produces the same revision on macOS and Linux. 

{ "components": { "website": {}, "api": {} }, ... }
{ "components": { "api": {}, "website": {} }, ... }

Both normalize to one canonical document and one revision.

Code walkthrough

1. Identity migration

Migration 2 rebuilds the claims table with component and endpoint in its uniqueness constraint. Every old service becomes a component with endpoint default. Claim IDs are copied unchanged, so leases, runs, listener fingerprints, and history keep pointing to the same entities. Foreign keys are disabled only around the immediate rebuild transaction, checked before commit, and restored in a finally block.

2. Strict definitions

The version-1 schema models components, published or internal endpoints, preferred or exact allocation intent, dependency aliases, and declarative Docker service/container-port facts. It rejects unknown fields, contradictory ports, missing dependency targets, and Docker endpoint metadata without a Docker component. Names must already be trimmed, preventing two record keys from collapsing during parsing.

3. Atomic registration

Migration 3 adds stacks, immutable definition revisions, and endpoint-to-claim links. Apply prevalidates all published endpoints before writing. It reuses a matching sticky legacy claim, refuses an ephemeral claim or conflicting exact assignment, preserves an existing assigned port, and records one history event. Reapplying the same revision performs no writes and returns changed: false.

4. Public surfaces

The socket server exposes apply, list, and show routes. The official client canonicalizes worktree paths and preflights the daemon's stack-definitions-v1 capability, then the mutation negotiates again server-side. Commander adds stacks apply/list/show/status with the existing versioned JSON and exit-code conventions.

What this deliberately does not do

  • It does not allocate a complete generation or begin an activation.
  • It does not start, stop, or health-check a project process.
  • It does not invoke Docker or treat Docker metadata as ownership evidence.
  • It does not generate sandbox discovery documents.
  • It does not advertise capabilities for any of those later operations.

That narrow boundary is important. Clients can test for exactly the behavior implemented by this slice. Later PRs can add generations, activation leases, scoped resolution, Docker evidence, and desktop actions without pretending they already exist.
