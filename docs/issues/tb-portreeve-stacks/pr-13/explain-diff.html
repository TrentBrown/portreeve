Background

A Portreeve stack is not a process supervisor. It is a durable, versioned network plan for one Git worktree. The checked-in definition names components, endpoints, and dependencies. Portreeve allocates one immutable generation of host ports. A project-owned launcher consumes short-lived leases, starts the actual processes or containers, and confirms them with fresh evidence.

Apply strict definition
Prepare immutable generation
Begin leased activation
Launcher starts and confirms providers
Resolve, reconcile, end, prune

This division of labor is the central safety boundary. Portreeve knows which address belongs to which logical endpoint. The launcher knows commands, environment, Compose topology, health checks, and shutdown order. Sandboxes receive a redacted read-only address document, never the control socket.

Two kinds of live evidence

Host process

lsof supplies fresh listener PIDs. Portreeve combines that with process start time, executable, confirmed run, and lineage. Stored PIDs are hints, never authority.

Docker provider

Fresh Docker inspection proves the exact running container, activation labels, loopback host publication, allocated host port, and declared container port. Process lineage is intentionally irrelevant.

The portability discovery: Docker Desktop commonly exposes a userspace listener that lsof can see. Linux Docker Engine may publish through kernel NAT, where the address works but no userspace process is listening. Treating a missing Linux listener as a dead publication was a false negative.

Intuition

Imagine a stack with website.http and api.http. Portreeve allocates host ports 10241 and 10240. The launcher binds the website process to 10241 and publishes an API container as 127.0.0.1:10240 → 3000/tcp. The website resolves its declared backend alias to 10240. 

{
  "website": { "own.http": "127.0.0.1:10241" },
  "backend": {
    "host": "127.0.0.1:10240",
    "dockerNetwork": "api:3000"
  }
}

Confirmation is not a health check. The launcher may wait for an HTTP health response before starting the website, but Portreeve asks a narrower question: “Does fresh, binding-appropriate evidence identify the provider that this activation leased?” That distinction keeps Portreeve portable and prevents it from absorbing every project's startup policy.

Code walkthrough

1. Native harness

scripts/verify-stack-feature.js behaves like a temporary trusted launcher. It starts a disposable process listener and uniquely named container, but all Portreeve operations travel through the official JavaScript client. A finally block owns exact cleanup.

2. Release gate

Linux x64 and ARM64 native jobs run bun run stacks:verify before lifecycle verification. macOS Docker Desktop remains a manual product smoke because hosted macOS runners do not provide it.

3. Platform-correct Docker evidence

Docker confirmation no longer requires an lsof listener. Exact container inspection remains mandatory. Inventory also queries Docker for a known Docker run even when the listener list is empty.

4. Adoption guides

The public desktop guide explains trust and lifecycle boundaries. The mixed-stack example explains how a launcher maps returned leases and resolutions into processes, Compose, and sandbox discovery files.

Why the evidence change is still safe

The removed check was not the check that identified the container. The container ID still acts only as an inspection key. Confirmation recomputes labels from durable stack state, requires the container to be running, and verifies the exact host-to-container TCP mapping. A stale ID, wrong label, stopped container, wildcard publication, wrong host port, or wrong container port still fails. Meanwhile, process reclamation continues to require fresh lsof evidence and never signals Docker infrastructure.
