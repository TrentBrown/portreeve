Portreeve · PR #11 · P6 / I-5

Recovery without heartbeats. Pruning without reclamation.

This change lets Portreeve recover when a stack launcher disappears and safely forget old stacks whose worktrees no longer exist. Fresh process, listener, and Docker observations remain the authority at every destructive boundary.

Background

The durable record can outlive the thing it describes

Portreeve already persisted a confirmed activation, but a launcher crash could leave that activation marked live forever. A stored PID cannot resolve the ambiguity: it may be stale or reused. A stored Docker container ID has the same problem unless Docker freshly confirms what that ID represents.

Old failure mode The launcher vanishes, providers stop, and the durable activation continues blocking the next attempt.
Recovery requirement Re-observe every confirmed provider. Keep the activation live if any provider survives or cannot be observed conclusively.
Cleanup requirement A missing worktree is only a candidate. Portreeve must also rule out leases, runs, listeners, and matching containers before deleting metadata.
Intuition

Evidence narrows permission; it never expands it

Recovery is deliberately asymmetric. Conclusive absence permits a transition to lost. Positive or ambiguous evidence preserves the live state. The same idea governs ending and pruning.

1. Inspect afresh

Use lsof, process-instance evidence, and exact Docker inspect and publication facts.

→

2. Preserve on doubt

Any active or unknown provider keeps the activation live and blocks end or prune.

→

3. Change on absence

Only all-gone evidence releases stored runs and records the activation as lost.

No kill path is involved. Stack pruning never invokes process reclamation, unsafe eviction, Docker stop, or Compose. It removes Portreeve records only after repeated evidence checks.
Code

Two services, one conservative boundary

Coordination service reconcile(), inspectProviders(), and evidence-gated end() share the process and Docker evaluator.
Administration service prune() plans candidates and blockers, then repeats external evidence checks immediately before deletion.
Registry transaction deleteStack() rechecks live database work, deletes the graph and claims atomically, and appends durable history.

Reconciliation rule

// A durable activation changes only when every fresh provider result is gone.
const providers = await inspectProviders(activation.id);

if (providers.length > 0 && providers.every(p => p.status === 'gone')) {
  return registry.markStackActivationLost(activation.id, providers);
}

return { changed: false, activation, providers };

Prune execution rule

// Planning is informative. Execution proves the candidate again.
if (await pathExists(stack.workspaceRoot)) skip('workspace-reappeared');
await reconcileLiveActivationWhenPossible();

const fresh = await evaluateFilesystemListenersRunsAndDocker(stack);
if (fresh.reasons.length > 0) skip(fresh.reasons);

registry.deleteStack(stack.id); // immediate SQLite transaction rechecks live work

Safety boundary

What happens in the awkward cases?

PID was reused Fresh inventory no longer maps the listener to the stored run. Recovery does not accept the stored PID as authority; a live replacement listener also blocks pruning.
Docker is unavailable Provider state becomes unknown and Docker-defined prune candidates are blocked. Lack of evidence is not absence.
Container runs, listener flickers Exact fresh Docker labels and publication keep the provider active even when the host listener is momentarily absent.
Worktree reappears Execution skips the candidate after a second filesystem check.
Listener or container appears Execution-time inventory or Docker discovery adds a blocker and preserves the stack.
Database state changes The immediate deletion transaction refuses a new live activation, pending lease, or confirmed run.

Quiz

Check the authority model

1. A stored PID no longer exists. Is that alone enough to mark the activation lost?

No. Portreeve inspects the current listener and process instance. The stored PID is context, not live authority.

2. Docker inspection succeeds but lsof temporarily shows no listener. What happens?

If the running container still has the exact expected labels and loopback publication, the provider remains active.

3. Does --json authorize a noninteractive prune?

No. Noninteractive execution still requires --yes; JSON only changes output framing.

4. Can stack pruning stop a process or container it discovers?

No. Any live or unknown evidence blocks deletion. Pruning contains no reclamation or container-lifecycle path.

5. Why are both service revalidation and a registry transaction needed?

The service owns fresh filesystem, listener, and Docker observations. The registry owns atomic durable-state checks and deletion. Neither layer can safely replace the other.
