Background

The product problem

Development services share localhost's port space. A single frontend can usually claim port 3000 without ceremony; three agents running three worktrees of the same stack cannot. PortReeve supplies one per-user authority that assigns stable endpoints and verifies their real process or container ownership. Desktop, CLI, MCP, and the JavaScript client are peers of that authority. Project tools still start and supervise the services.

GoodDesktop driver

Desktop injects resolved endpoints into familiar shell commands.

You → Desktop → server → command → services

BetterGenerated launcher

A planned launcher will remove Desktop from the runtime path.

You → launcher → server → services

BestProject integration

Project tooling requests and confirms bindings in its own control flow.

You → project tooling → server → services

The documentation problem

Desktop Overview had grown into the strongest explanation of that model, while README was comparatively terse. Copying Desktop HTML into Markdown, or generating one surface from the other, would make routine visual editing harder. Maintaining two unrelated documents would invite conceptual drift. The approved design therefore separates shared meaning from surface-specific expression.

Code walkthrough

1. The semantic contract

docs/product-overview-contract.md defines the eight meanings, each surface's responsibility, and the same-PR maintenance rule. It explicitly rejects shared rendering and literal-copy requirements.

2. The public landing page

README.md now carries the complete story: the localhost problem, name provenance, clients, integration paths, stacks, lifecycle, ownership evidence, boundaries, and truthful source-based next steps.

3. Native visuals

Six directly authored Mermaid blocks explain authority, three integration sequences, a client/API/database chain, and the activation lifecycle. A current Desktop screenshot makes the primary experience tangible.

4. Desktop landmarks

apps/desktop/renderer/index.html gains eight data landmarks and narrow accuracy corrections. Existing buttons remain native Desktop navigation; no Markdown reader or generator enters the renderer.

5. Structural tests

test/docs/product-overview-parity.test.js derives the approved IDs, checks both surfaces, and contains intentional omission cases. It also protects clients, paths, screenshot alt text, diagrams, and renderer independence.

6. Existing contracts

Desktop and release-documentation tests were adjusted for accurate “server” terminology, foreground operation, planned launchers, and line-wrapped unsupported-capability statements.

Why the screenshot is not pixel-tested

A screenshot's usefulness is editorial: it should be current, legible, and representative. Pixel comparisons would make harmless rendering changes expensive while still failing to judge whether the image tells the right story. The suite checks its existence and meaningful alt text; the contract assigns visual fidelity to review.
