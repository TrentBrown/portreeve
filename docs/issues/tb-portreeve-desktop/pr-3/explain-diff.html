Making the first release path real

This change turns a plausible release workflow into one that has run successfully on every supported architecture—without publishing a package prematurely.

Contents: Background Intuition Code Quiz

Background

The larger system

Portreeve is a per-user authority for development ports. Its compiled CLI can run a server manually, install a managed copy, and delegate supervision to launchd on macOS or systemd --user on Linux. A JavaScript client communicates through the public socket protocol; it does not make privileged in-process calls.

A release therefore has more to prove than “Bun compiled four files.” A cross-compiled executable may have the right header and checksum while still failing on its destination OS. Portreeve's release gate executes the complete lifecycle natively: install, start, upgrade, restart, stop, uninstall, purge, and reinstall.

Build Compile four executables and pack the public npm client.
Transport Move one immutable artifact bundle between jobs.
Execute Run the matching binary and native supervisor lifecycle.
Policy Verify tag, visibility, npm identity, and version availability.
Publish Create npm and GitHub artifacts only for a release tag.

Why the old workflow stopped short

Linux ARM64 depended on a self-hosted runner that did not exist. Publication assumed npm credentials that were not configured. Once a real hosted matrix was run, GitHub artifact transport exposed another property: downloaded files have ordinary 0644 mode, even when the original was executable.

Important distinction: a checksum authenticates file bytes, not Unix metadata. Restoring mode to 0755 does not change the checksum or weaken binary-format verification.

Intuition

The central idea is to make every prerequisite observable before the irreversible step. The workflow may build and test on any branch, but publication jobs exist only for a v* tag and only after the policy job proves that the repository is public, npm credentials are valid, and the exact package version is absent. 

branch dispatch
  → build
  → four native lifecycle jobs
  → stop (no publication)

v0.1.0 tag
  → build
  → four native lifecycle jobs
  → release policy
  → npm + GitHub publication

The Linux purge failure illustrates the same philosophy. The purge guard found systemd-created logs with mode 0664. The tempting response would be to relax deletion safety. This change instead fixes creation: Portreeve exclusively pre-creates both logs at 0600 and places UMask=0077 in the unit. The safety rule remains uncompromised.

Code walkthrough

1. Release workflow

.github/workflows/release.yml replaces the unavailable self-hosted ARM64 selector with ubuntu-24.04-arm. After artifact download, it restores executable modes and then runs the unchanged checksum, format, native server, and lifecycle verifier. GitHub-maintained actions move to their current Node 24-backed majors. 

- runner: ubuntu-24.04-arm
  platform: linux-arm64

- name: Restore executable artifact modes
  run: chmod 755 dist/release/portreeve-v*

2. Publication policy

The policy job now configures the npm registry, calls npm whoami, and distinguishes the expected “version not found” response from network, authorization, or registry failures. Both publishing jobs depend on this one gate. 

if npm view "portreeve@$version" succeeds:
  refuse: version already exists
else if the failure is not E404:
  refuse: registry evidence is unreliable
else:
  publication may proceed

3. Private supervisor logs

prepareRuntimeDirectories accepts optional native supervisor log paths. Missing logs are created with exclusive wx semantics and mode 0600. Existing paths must be regular, non-symlink files owned by the current user, private from group and other users, and writable by their owner.

This is both a lifecycle fix and a security improvement: the native supervisor cannot follow a pre-positioned symbolic link when it opens stdout or stderr.

4. Tests and documentation

Tests assert private file creation, refusal to repair permissive files silently, the systemd umask, current action majors, hosted ARM64, npm preflights, and absence of the self-hosted dependency. Installation documentation now describes the bootstrap credential and the planned migration to npm trusted publishing after the package exists.

What this PR does not do: it creates no tag, npm package, or GitHub Release. The first public publication remains an explicit operator step after merge and npm authentication.
