From status window to safe control plane

This change turns the secured, read-only Electron shell into the complete two-view management workflow—without moving lifecycle or deletion authority out of the Portreeve CLI.

Background

Portreeve is a per-user authority for development ports. Its server owns claims and leases; its CLI owns native supervision and complete reset; its JavaScript client speaks to the server over the private socket. The desktop application is deliberately only a management client.

Before this PR, the chain stopped at observation. The renderer could request a snapshot or refresh and could display a small status/inventory table. It could not install, start, stop, upgrade, uninstall, or reset Portreeve.

The governing constraint: making the UI convenient must not make the renderer powerful. A compromised renderer should still be unable to choose an executable, invent CLI arguments, obtain a reusable purge token, or delete a path itself.

Intuition

The core idea is to treat each button as one narrow capability. “Restart” does not send {action, args}. It invokes a fixed restart() preload method, whose main-process handler can only run the verified bundled executable with restart --json.

Ordinary lifecycle

The CLI returns before/after evidence and a structured outcome. The coordinator reduces that to a safe step result, refreshes all evidence, and gives the renderer the new snapshot.

Complete reset

The CLI previews exact paths and returns an evidence hash. Main memory keeps the hash. The renderer receives only display evidence and must supply the literal typed word DELETE.

Two-phase reset with toy evidence

preview → { allowed: true, paths: [database, logs, socket] }
main only → token = sha256(marker + lifecycle + filesystem)
renderer → user types DELETE
execute → CLI rebuilds preview and compares token
drift?  → refused: preview-evidence-changed
same?   → remove exact tree and report removed/retained/missing
Why consume the token before execution? Even a timeout or malformed CLI response cannot leave a reusable destructive authorization behind. A second attempt requires a new preview.

Code walkthrough

1. Strict desktop contracts

shared/schemas.js adds runtime schemas for lifecycle action results, purge previews/results, the typed execution request, richer port detail, and independent desktop/bundled/managed/running versions. These schemas define the maximum data the renderer can receive.

2. Fixed CLI adapter

main/cli-adapter.js validates canonical CLI envelopes for all lifecycle operations. Purge preview stores its token in a closure; the returned object omits it. The adapter uses the exact verified executable with shell execution disabled.

3. One serialized coordinator

main/coordinator.js makes refresh and mutation mutually exclusive. A refresh that arrives during a mutation awaits the mutation’s final snapshot. A second mutation is refused as busy. Install-and-Start is explicitly two steps and becomes partial when installation changed the machine but start or final PID/health verification failed.

4. A narrow bridge and state-derived UI

5. Useful port evidence without raw commands

The Ports view filters by port, classification, project, service, or workspace name. Selecting a port shows claim mode and lifecycle, run root, listener addresses, PID lineage, UID, start time, executable basename, and working directory. Raw process command lines and full executable paths remain excluded.

6. Separate desktop runtime storage

Packaged inspection discovered Electron writing Chromium caches into the CLI’s marker-bound application home. That made the CLI correctly refuse reset. Startup now assigns Electron a distinct Portreeve Desktop user-data directory before readiness, so desktop caches never enter the service deletion tree.

Important safety cases

Manual server

The UI offers an explicit Stop manual server action, never silent adoption. Uninstall is withheld. CLI evidence remains final.

Ambiguous or stale lifecycle

Mutation actions are withheld when execution mode is ambiguous or lifecycle refresh failed. Inventory-only staleness does not hide safe onboarding.

Unavailable uninstall

A boundary review found rendering re-enabled the absent-state Uninstall button. The final code centralizes canUninstall and preserves the disabled state.

Prerelease upgrade

A second review found lexicographic prerelease ordering. The final comparator treats rc.10 as newer than rc.2 and ignores build metadata.

Evidence boundary: the packaged ARM64 smoke exercised real rendering, cancellation, unavailable-state disabling, and reset refusal/preview. Successful native mutations remain adapter/coordinator tested here and must be recorded end-to-end on disposable ARM64/x64 release hosts in P9–P10.
