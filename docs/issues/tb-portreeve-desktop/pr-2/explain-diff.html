A trustworthy control surface for Portreeve

This change turns lifecycle management and complete reset into explicit, runtime-validated contracts. It is the safety and integration foundation on which the future desktop application will stand.

Background

Portreeve is a per-user local authority for development ports. A CLI can run the server manually in a terminal, or native supervision can keep it alive through launchd on macOS and systemd-user on Linux. A private Unix socket carries the service protocol. These are related facts, but they are not the same fact.

Before this PR, lifecycle commands returned several command-specific shapes. A future desktop main process would have needed to infer whether an executable was installed, whether a supervisor was active, whether a socket responder existed, and whether that responder was actually the supervised process.

InstallationIs the managed executable absent, installed, or unsafe?
SupervisorIs the native definition unavailable, inactive, starting, active, or failed?
SocketIs the protocol endpoint unavailable, healthy, unhealthy, or incompatible?
Effective modeDo fresh PID and mode claims prove manual, supervised, none, or ambiguous?
The key authority rule: Portreeve calls a responder “supervised” only when its self-reported mode and PID agree with the supervisor observed now. A stored PID is never sufficient.

Intuition

Think of lifecycle status as a photograph assembled from three cameras. One camera sees the executable, one sees launchd or systemd, and one speaks to the socket. A broken camera does not erase the other two photographs. The result carries each observation and its limitation.

Mutations use two photographs: one before and one after. If an operation refuses to begin, both may be equal. If it changes supervision but fails health verification, the result says partial and preserves the evidence rather than reducing everything to an exception string.

1. ObserveCapture strict installation, supervisor, socket, mode, and version evidence.
→
2. MutateEnforce manual-server, incompatibility, ownership, and downgrade rules.
→
3. Observe againReturn succeeded, no-change, refused, partial, or failed with both snapshots.
{
  "operation": "stop",
  "outcome": "refused",
  "changed": false,
  "before": { "mode": "manual" },
  "after":  { "mode": "manual" },
  "error":  { "code": "conflict" }
}

Manual shutdown is intentionally named stop-manual. Ordinary stop controls native supervision only. That small naming distinction carries a useful consent boundary.

Code walkthrough

1. Canonical lifecycle schemas

src/supervision/schemas.js defines strict Zod schemas for every layer, semantic versions, stable errors, and the common mutation result. manager.status() gathers the layers concurrently and validates the assembled snapshot before it crosses the CLI boundary.

2. Evidence-based lifecycle manager

The manager now keeps unavailable and incompatible observations inside status. It refuses mutation when managed installation or supervisor evidence is unsafe, refuses to adopt a manual responder, and compares source, managed, and running versions before replacing an executable. 

supervisor PID 4242
socket claims supervised PID 4242  => supervised

supervisor PID 4242
socket claims manual PID 9000      => ambiguous

no active supervisor
socket claims manual PID 9000      => manual

3. Stable CLI behavior

All lifecycle mutations now emit the same result shape. Evidence-bearing refusals still go to stdout with the appropriate nonzero exit band. Usage errors—such as a malformed purge token—remain top-level CLI errors.

4. Release verification

The release verifier parses the production schemas and extends the real native lifecycle through uninstall, marker-bound purge, and clean reinstall. It runs the compiled artifact rather than importing source implementation shortcuts.

Reset safety

Complete reset is deliberately not “remove this directory.” Portreeve first proves that the directory is its own private state, then binds the proposed deletion to a deterministic SHA-256 token.

PreviewValidate marker, canonical root, owner, modes, symlinks, live state, supervisor definition, and every path.
→
Confirm tokenRecompute the evidence. Any pre-execution difference refuses the operation.
→
Delete safelyStop supervised state, revalidate, reject new paths or retained definitions, remove marker and root last.
The token is not a password. It is a compact identity for the evidence the user inspected. The desktop will add its own typed DELETE confirmation; the CLI remains the final filesystem authority.

Review discovered two shutdown-window hazards. The final code refuses a path created after confirmation, and it refuses to claim success if a supervisor adapter leaves its definition behind. It also validates the contents of a pre-marker bin directory before claiming it, so an innocent file cannot become Portreeve-owned merely by being nested under a recognized top-level name.
