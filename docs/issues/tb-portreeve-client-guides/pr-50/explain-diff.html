One contract, three useful forms

PortReeve can now derive complete CLI and MCP reference material directly from the interfaces it ships, validate authored guidance as inert content, and commit a version-bound Desktop bundle. This is the foundation for the human guides and Desktop tabs that follow.

Safety model

Documentation is data, not runtime authority. The compiler accepts a deliberately small Markdown subset and rejects active or ambiguous content.

author prose
  → validate markers and links
  → reject HTML / unsafe URLs
  → compile to inert nodes
  → render only trusted components

The Desktop will not parse Markdown at runtime, fetch documentation from the network, or execute examples found in prose.

Why exact schemas are retained

The MCP reference is large because the tool schemas are the public contract. Summaries are useful for onboarding; exact required fields, closed objects, enums, and output shapes are what let developers and agents act correctly. The bundle stores generated reference structurally rather than duplicating it inside the authored AST.

Review outcome

A review caught one raw-HTML edge case: a tag after ordinary text could bypass a line-start check. The validator now removes inline-code spans and rejects HTML-shaped tags everywhere else on a line. A regression test proves the fix.

Result: no remaining correctness, security, regression, or test-gap findings.

Knowledge check

1. Why generate from Commander and the MCP registry?

They are the shipped interfaces. Deriving documentation from them turns missing coverage and contract drift into test failures.

2. Does this slice redesign the guides?

No. It seeds valid generated regions and the safe pipeline. Complete onboarding, recipes, comparison, and troubleshooting are the next slice.

3. Can authored Markdown inject HTML into Desktop?

No. Raw HTML and unsupported Markdown fail generation, and Desktop receives inert structured content rather than raw Markdown or HTML.

4. What prevents a stale Desktop guide from shipping?

The freshness check compares regenerated Markdown and bundle output with committed artifacts, and Desktop packaging runs that check.

5. Are feature-level rubric items complete?

Not yet. I-1 passes its planned contribution; authored guides, Desktop experiences, README integration, and packaged offline proof remain explicit later slices.
