Background

PortReeve has three representations of the same client documentation. The runtime CLI and MCP catalogs describe the public contracts. Stable Markdown files make those contracts readable on GitHub. A committed JavaScript data bundle makes the same material available to the Desktop renderer without fetching or parsing prose at runtime.

1 · Contracts 49 CLI leaves and 51 MCP tools carry documentation metadata.
2 · Generator Strict validation produces Markdown and an inert data bundle.
3 · Package Electron ASAR contains the renderer, guide view, and generated bundle.
4 · Desktop DOM-only rendering combines static content with fresh lifecycle evidence.

Earlier slices verified each part from source. The subtle remaining question was whether the assembled application still contained the expected path. A source file can be correct while a package script omits it, an import changes, or a later refactor quietly introduces a network fetch. This slice verifies the release-shaped artifact rather than trusting the source tree alone.

Intuition: inspect the box, not the packing list

Imagine shipping a first-aid kit. Checking the warehouse inventory proves that bandages exist somewhere; opening the sealed kit proves that the user actually receives them. The strengthened package verifier opens app.asar and extracts the exact modules involved in the guide path. 

app.asar
├── renderer/renderer.js              imports the generated guide
├── renderer/client-guide-view.js     builds safe DOM elements
└── renderer/generated/client-guides.js
    └── generatedForVersion: '0.1.0'
        cliCommands: 49
        mcpTools: 51
Fail closed: the package is rejected if a required module or marker is absent, the version/count attestation is stale, or the guide runtime contains a documentation fetch, Markdown parser, DOM parser, or HTML insertion path.

Live evidence is deliberately separate. If no daemon is installed, the bundled guide remains useful. If evidence is stale and the running version is incompatible, the model reports both facts instead of collapsing them into a generic error. Static instruction and dynamic observation can therefore fail independently and remain understandable.

Code: package attestation

desktop-package-lib.js now extracts the renderer entry point and guide view in addition to the generated bundle. It checks the import and rendering path, then scans the combined guide runtime for prohibited capabilities.

This is stronger than checking only filenames: a bundle can exist but be orphaned. Requiring the import, view constructor, and installation-evidence call proves the path is connected.

Code: deterministic formatting

The generator now passes the repository's formatting contract explicitly: 88-column width, semicolons, single quotes, and trailing commas. Generated output no longer depends on where or how Prettier discovers configuration.

The large generated diff is therefore mechanical quote normalization, not a change to the 49-command or 51-tool guide contents.

Code: degraded evidence

New model tests cover two important states: a fresh snapshot with no lifecycle installation and a stale snapshot with an incompatible running daemon. Both retain the bundled version and usable static documentation.

Code: public claim boundary

A cross-document release test reads the README, client guides, protocol and stack documents, and mixed-stack example. Former positive Sandbox phrases are prohibited, while explicit non-support and the generic endpoint snapshot description are required.
