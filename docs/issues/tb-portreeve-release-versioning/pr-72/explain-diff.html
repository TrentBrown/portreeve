PortReeve pull request #72

One release, one identity

Preview.3 was a preview in GitHub but looked like plain 0.1.0 after installation. This change makes the operator's requested semantic version the identity users and update systems actually observe.

BackgroundIntuitionCodeQuiz

Background

A software release has several names hiding inside it: the Git tag, executable filename, CLI --version, package version, Homebrew formula version, Desktop update version, and macOS bundle version. PortReeve's first previews used 0.1.0-preview.3 for the release tag but left distributed components at the checked-in development version, 0.1.0.

Before

GitHub knew about preview.2 and preview.3. Homebrew and Desktop saw both as the same 0.1.0 product. A newer preview therefore had no reliable upgrade identity.

After

Every PortReeve release output says preview.4. The source still says 0.1.0, so ordinary development remains simple and the clean-source release gate remains meaningful.

Why not edit every package first? Release preparation requires a clean, pinned source tree. Mutating several package files as ceremony creates drift and makes it easier for one component to be forgotten. The build now derives all release identity from one approved input.

Intuition

Think of 0.1.0 as the source's compatibility base and 0.1.0-preview.4 as the immutable shipment label. The release engine first proves that the shipment belongs to that base, then stamps the full label into every artifact.

macOS adds one wrinkle. Apple's conventional application version remains numeric 0.1.0. PortReeve embeds a separate portreeveReleaseVersion with the full prerelease and uses that for its own reporting and update comparison.

Code walkthrough

1. A single coordination rule

scripts/release-version.js validates the requested semantic version, extracts its core, and checks every source package against that core. Its Bun plugin replaces only PortReeve's two version modules while immutable binaries are compiled.

2. Artifacts inherit the release identity

scripts/release-build.js uses the full release version for native filenames, compiled CLI behavior, the client archive, formula, and manifest. The client is copied to a unique temporary directory before its package metadata is rewritten, then that directory is removed in a finally block.

3. Desktop separates product and Apple identities

scripts/package-desktop.js injects the coordinated version into the main-process bundle, generated guide attestation, verification record, and packaged metadata. Electron reads that metadata at startup. Packaging still passes the numeric base to Apple's bundle field.

4. Verification follows the manifest

The release and MCP verifiers now compare runtime behavior to the coordinated manifest identity. They still enforce checksums, executable format, executable permission, lifecycle behavior, Desktop contents, and update compatibility.

Deliberate non-change: preview.3 remains immutable. The fix starts with the next release; it does not rewrite a public tag or its assets.
