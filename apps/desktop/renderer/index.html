        Overview
        
            
        What is PortReeve?
        
            
        
              Localhost port conflicts, solved.
              PortReeve gives every development service a stable TCP address and
              verifies which process or container actually owns it.
            
        
            
        
              
        
                
        The problem
        
                
        
                  On one development machine, services share localhost's TCP port space.
                  Hostnames do not by themselves let two listeners claim the same local
                  address and port. Modern agentic development multiplies the pressure:
                  several agents may run independent copies of the same stack from
                  different Git worktrees, while every copy reaches for the same
                  familiar defaults.
                
        
              
        
              
        
                
        The name
        
                
        
                  A reeve was a person entrusted with local administration, and
                  the office took different names—such as shire reeve, borough reeve,
                  and portreeve—according to the place or responsibility. The title
                  shire reeve survives in contracted form as the modern word
                  sheriff. A portreeve governed a port or market
                  borough, where port could mean a market town, not only a
                  seaport. PortReeve is the modern local official for your machine's
                  network ports.
                
        
              
        
              
        
                
        One authority, several peer clients
        
                
        
                  One supervised PortReeve server runs for the current operating-system
                  user. The Desktop app, portreeve CLI, official JavaScript
                  client, MCP integrations, and project launchers are all clients of
                  that authority—and peers of one another. PortReeve assigns addresses
                  and verifies bindings; your project tooling remains responsible for
                  starting, supervising, and judging the health of your services.
                
        
              
        
            
        
          
        
        
        

        
        
          
        
            
        Choose a client
        
            
        Four peer clients, one PortReeve authority
        
            
        
              Choose the client surface that belongs in your workflow. Each is a peer of
              the others: all use the same per-user daemon and durable port state, and
              none creates a second PortReeve authority.

        What project integration adds
        
              
        
                PortReeve's confirmation guarantee is the same wherever the verified
                activation protocol is used; a generated launcher can obtain the same
                ownership proof. Project integration removes the extra adapter boundary:
                the project tooling that owns provider lifecycles also owns lease
                acquisition, binding confirmation, failure handling, and cleanup.
              
        
              
        
                Confirmation proves ownership, not application readiness.
                It succeeds only after fresh listener or Docker evidence shows that the
                expected provider owns the binding. Whether the application can handle a
                real request remains a project-owned health decision.
              
        
            
        
          
        
        
        

        
        
          
        
            
        Stacks
        
            
        
              Your local development stack already exists
            
        
            
        
              The frontend, APIs, workers, and supporting services you run together
              locally mirror the system you deploy. PortReeve does not invent a new kind
              of stack; it gives that familiar topology stable names and a coherent set
              of local network addresses.
            
        
          
        

          
        
            
        
              
        Name relationships, not port numbers
        
              
        
                A portreeve.stack.json file names the stack's components,
                the endpoints each component publishes, and the endpoints its peers
                need. It contains no current port assignments.
              
        
              
        
                One selected development root—often a Git worktree—represents one
                independently runnable instance of that stack. PortReeve keeps the
                instance's assignments in its own durable state.
              
        
            
        

            
          
        

          
        
            
        
              
        Within one stack
        
              
        Coordinate service dependencies
        
              
        
                PortReeve allocates published endpoints together and gives every
                consumer the matching dependency addresses. A client therefore learns
                the API address chosen for this run; the API learns the corresponding
                database address. No service has to guess another service's port.
              
        
            
        
            
        
              
        Across stack instances
        
              
        Prevent port collisions
        
              
        
                A second worktree or agent can run the same topology with a different,
                equally coherent generation. The component and endpoint names stay the
                same while their localhost ports remain isolated from every other
                running instance.
              
        
            
        
          
        

          
        
            Project tooling still owns execution.
            PortReeve coordinates allocations, dependency addresses, leases, and binding
            evidence. Your launcher or project tooling decides startup order, starts the
            services, and determines when they are healthy.
          
        
        
        

        
        
          
        
            
        Architecture
        
            
        
              One authority, project-owned execution
            
        
            
        
              The integration tool changes between Good, Better, and Best. The actors,
              PortReeve concepts, and startup sequence below do not.
            
        
          
        
          

          
          
        
            
        Ownership is not readiness
        
            
        
              PortReeve can confirm that an endpoint is listening and that the expected
              process or container owns it. It does not claim that the application is
              healthy or ready to serve requests.
            
        
          
        
        
        

        
        
          
        
            
        Diagram details
        
            
        Follow the concepts deeper
        
            
        
              These notes expand the sequence and state-model diagrams without adding
              more steps to their first reading.
            
        
          
        
          
        
            Claims, preparation, and leases
            
        
              
        
                Apply links every published endpoint to a durable claim. Prepare uses
                those claims to allocate one complete generation without starting a
                lease deadline. Begin then issues an activation-scoped lease for every
                selected endpoint. For a standalone service, withPort()
                hides the corresponding acquire, bind, and confirm negotiation.
              
        
            
        
          
        
          
        
            Generations, activations, resolve, and confirm
            
        
              
        
                One independently runnable stack belongs to each root. Its components
                expose named endpoints and declare dependencies in
                portreeve.stack.json; current port numbers remain in
                PortReeve. A generation keeps the whole stack on one coherent endpoint
                plan, while each start attempt receives a new activation. Resolve reads
                addresses from that generation; Confirm separately proves that the
                expected process or container actually owns a leased endpoint.
              
        
            
        
          
        
          
        
            Process and Docker evidence
            
        
              
        
                Fresh lsof listener evidence is live truth for host ports;
                stored process IDs are context, not authority. Docker confirmation uses
                running-container state, exact labels, and publication evidence.
                PortReeve does not stop project processes or containers itself.
              
        
            
        
          
        
          
        
            Desktop, CLI, client, and server
            
        
              
        
                There is one per-user installation and authority, not separate desktop
                and CLI servers. Desktop, CLI, and the official JavaScript client use
                the same private HTTP/JSON socket contract; only the server mutates
                SQLite.
              
        
            
        
          
        
          
        
            What PortReeve deliberately does not do
            
        
              
        
                PortReeve is not a general project-process supervisor, Docker Compose
                replacement, startup-order engine, secret manager, application health
                system, reverse proxy, DNS server, or sandbox control plane. It can
                verify ordinary Docker-backed endpoints, but it does not currently
                provide Docker Sandbox orchestration or integration.
